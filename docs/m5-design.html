cmx-flow M5 设计方案 · 子流程 · 按组织机构路由

主流程一个「调用节点」不写死调哪个子流程，而是按运行实例的组织机构动态选择——各组织维护各自的子流程定义，同一主流程在不同组织跑出不同的审批链。以 callActivity（调用活动）+ 组织路由实现。

M5.1 子流程机制：✅ 已落地实测 M5.2 组织路由：✅ 已落地实测 机制：callActivity 同步等待 继承：cmx_org.path 向上 不改：M1~M4 语义

要解决什么

到 M4 为止，一份流程定义在所有组织跑法一样。但真实审批里，同一个主流程，不同组织的中间环节不一样： 「报销审批」主流程里的「财务复核」子环节，总部走三级、北京分公司走两级、上海分公司外包给共享中心—— 每个组织的这段子流程各自维护、独立演进，主流程不该关心细节。

报销主流程（一份定义，全组织共用） start → 部门经理 → 【财务复核·子流程】 → 出纳打款 → end │ ┌─────────────────┼─────────────────────┐ ▼(org=总部) ▼(org=北京分公司) ▼(org=上海分公司) 总部财务复核 v1 北京财务复核 v1 上海财务复核 v1 三级会签 经理单签 外包共享中心

中间那个节点不写死调哪份子流程，只写一个逻辑 key（如 fin_review）。实例跑到这里，按自己的组织解析到该组织为 fin_review 绑定的子流程定义，启一个子实例跑。

一、机制：为什么是 callActivity + 组织路由

BPMN 有两种「子流程」，选型直接决定能否满足「各组织各自维护」：

形态是什么能否各组织各自设置结论
内联 subProcess 子流程块内嵌在主流程同一份 XML 里，随主流程一起部署 ❌ 所有组织共用同一内联块，改一处全组织变 不选
callActivity选它 主流程一个节点调用一份独立部署的流程，子流程单独维护、单独演进 ✅ 调哪份可由「组织」决定 → 各组织绑各自的子流程 选
核心创新点：标准 callActivity 的 calledElement 是写死的流程 key。M5 把它改成逻辑 key + 组织路由—— 节点写 cmx:calledKey="fin_review"（逻辑名，不是具体定义），运行期由 SubflowRouter 按实例的组织解析到具体子流程部署。这是「子流程网关」诉求的落地方式——不是新增一类网关，而是给 callActivity 加一层组织路由解析器。

二、组织路由：实例的组织如何选到子流程

复用 M4 已建立的模式——可注入解析器。M5 新增第四个扩展点 SubflowRouter（前三个：JavaDelegate·M1、Clock·M2.5、AssigneeResolver·M4）。

主实例（org = d_bj_fin 北京财务部）跑到 callActivity(calledKey=fin_review) │ ▼ SubflowRouter.resolve(calledKey, org) │ ├─ 1. 查 cmx_flow_subflow_binding WHERE called_key=fin_review AND org_id=d_bj_fin │ 命中？→ 用该绑定的 target_definition_key ────────────────┐ │ 未命中 ▼ │ ├─ 2. 沿 cmx_org.path 向上：d_bj_fin → d_bj → d_root，逐级找绑定 │ (向上继承) │ 命中最近的祖先绑定 ───────────────────────────────────────┤ │ 仍无 ▼ │ └─ 3. 兜底：org_id IS NULL 的默认绑定 ─────────────────────────────┤ ▼ 解析出具体子流程定义 bj_fin_review → 启动子实例（parent = 主实例）
① 精确绑定 本组织直接设置 ② 向上继承 沿 path 找最近祖先（就近） ③ 默认兜底 org_id 为空的全局默认
复用已有资产：组织树 cmx_org（M4.1 建，含物化 path）直接支撑「向上继承」——按 path 前缀就能一次查出某组织的所有祖先，选 path 最长（最近）的绑定。无需新建组织体系。

三、主子实例：父子关系 + 同步等待

子流程是一个独立的流程实例（有自己的令牌、任务、历史），通过 parent_instance_id 挂在主实例下。主实例在调用节点阻塞等待，子实例跑完才回主流程。

令牌机制（同步阻塞的关键）

主实例 M：令牌到 callActivity 节点 │ ├─ 1. SubflowRouter 解析出子流程定义 ├─ 2. 启动子实例 C：parent_instance_id=M，parent_token_id=当前令牌 │ 把主流程指定的输入变量传给 C（inputVars 映射） ├─ 3. 主令牌置 WAITING_SUBFLOW（新状态，像 userTask 一样挂起等待） │ ——主实例这一段落库提交（「等待态即提交点」，与既有事务模型一致） ▼ （子实例 C 独立跑：可含 userTask/会签/定时器…M1~M4 全部能力） ▼ 子实例 C 到 endEvent → 完成 → 触发回调 complete_subflow(C) │ ├─ 4. 把 C 的输出变量回写主实例 M（outputVars 映射） ├─ 5. 主令牌 WAITING_SUBFLOW → Active，离开 callActivity 沿出边前进 ▼ 主实例 M 继续：出纳打款 → end
为什么新增 WAITING_SUBFLOW 令牌态：它和 WAITING(userTask)/JOINING(并行合流) 并列——都是「令牌挂起、等外部信号」。区别是它的唤醒信号来自子实例完成，不是人工办结。子实例完成时按 parent_token_id 精确唤醒主令牌，天然支持一个主流程里多个 callActivity（甚至并行网关下并发调多个子流程）。

变量映射（主子数据传递）

callActivity 节点配 inputVars（主→子，启动时拷）与 outputVars（子→主，回归时拷）。默认全量传递，可配白名单。子实例的组织默认继承主实例组织（也可由 inputVars 覆盖，支持「主总部、子跑分公司」的跨组织场景）。

架构一致性：SubflowRouter 是继 JavaDelegate（M1）、Clock（M2.5）、AssigneeResolver（M4）之后的第四个「引擎向外的可注入扩展点」——引擎定义 trait，宿主注入实现（生产查 DB、测试用假 router）。子实例复用完整的 Engine 推进内核，无需为子流程另写一套执行逻辑——子流程就是「被一个父令牌等待着的普通实例」。

六、建议里程碑拆分

子步范围产出
M5.1 callActivity 同步子流程（先写死 calledElement，不路由）：NodeKind::CallActivity + WaitingSubflow 令牌 + 父子实例 + complete_subflow 回调 + 变量映射 子流程能跑通、能回主、变量能传——把最难的「主子实例同步」骨架立住
M5.2 组织路由：SubflowRouter 契约 + PgSubflowRouter（精确/继承/兜底）+ cmx_flow_subflow_binding 表 + instance.org_id；calledKey 逻辑名解析 同一主流程按组织跑不同子流程——兑现核心诉求

先 M5.1 立骨架（子流程机制本身）再 M5.2 叠组织路由（选哪份子流程），把「主子同步」的技术风险和「组织路由」的业务逻辑分开验证。管理台（绑定的增删改查）与 M5.2 并行。

七、风险 · 边界 · 非目标

关键风险

  • 递归深度：子流程里还能有 callActivity（孙流程）。需限制最大嵌套深度（如 ≤8）防死循环/爆栈，超限报错。
  • 子实例失败 / 取消传播：子实例被取消或报错时，主令牌怎么办？M5 先定「子取消 → 主令牌也终止（向上传播）」，可配后续。
  • 绑定解析歧义：同 called_key + 同 org 有多条启用绑定 → 取最新/报错，需定规则。向上继承时多个祖先都绑 → 取 path 最近（最长前缀）。
  • 孤儿子实例：主实例被删/终止但子实例还在跑。需级联处理或标记孤儿。
  • 历史归档：主子实例各自归档，但要能通过 parent_instance_id 串起完整审批链供审计。

本次非目标（M5 不做，留后续）

  • 异步子流程（发起后不等）——只做同步阻塞。
  • 内联 subProcess（嵌入式子流程块）——只做 callActivity 外部调用。
  • 多实例 callActivity（对一个集合并发调 N 个子流程）——先做单次调用，多实例复用 M3 机制留后续。
  • 子流程版本化 / 在跑实例迁移——沿用当前「单 key 单定义、部署覆盖」，版本化是独立议题。
  • 跨引擎 / 跨服务调用——子流程与主流程在同一引擎、同一库。
不动既有：M1~M4 的流程语义、表结构、测试全部不改。M5 全靠加列（幂等）+ 新表 + 新扩展点 + 新 NodeKind 变体接入；既有 44 内存测试须继续全绿作为回归基线。子流程复用现有推进内核，不分叉执行逻辑。
