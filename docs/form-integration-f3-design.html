2 · 两大先例精确核实 F3 靠这两根柱子

2.1 openWorkNode：5 级兜底开页链

// report-app-workbench.js:177 —— 逐字可复用
async function openWorkNode(workNode, sourceEl) {
  const candidates = [window, window.parent, window.top, globalThis].filter(Boolean)
  for (const target of candidates) {
    if (typeof target.openTab === 'function') { target.openTab(workNode); return true }
    if (typeof target.openWorkspaceNode === 'function') { target.openWorkspaceNode(workNode); return true }
  }
  // 兜底：POST /api/workspace-nodes → postMessage → CustomEvent('cmx-open-workspace-node')
}

这套链保证：无论 native-page 跑在门户主框架、iframe、还是 shadow-DOM host 里，都能把一个新工作区 tab 开出来。F3 的「点待办开表单」直接 import 这个函数。

2.2 doc-loader：现成的 props 驱动通用单据宿主

// doc-loader.js:419 —— "纯通用，不认识任何具体单据"
function readDef(ctx) {
  const p = (ctx && ctx.props) || {}
  const def = { domain: p.domain, application: p.application,
               module: p.module, file: p.file, dbId: p.dbId, apiPath: p.apiPath }
  const ok = def.domain && def.application && def.module && def.file
  return ok ? def : null   // 坐标齐 → 从 /api/doc/meta 驱动全部渲染
}
export default { defaultView: 'content',
  views: { async content(ctx) { const def = readDef(ctx); /* 载 meta+数据 */ } } }
关键洞察：F3 的表单宿主不用从零写——doc-loader 已经把「按 props 坐标、元数据驱动、动态渲染 N 层主从单据」做完了。F3 的 task-form 页 = doc-loader 的载入能力 + 额外的任务上下文（formKey/taskId/mode） + 办结动作。第一版可以直接 fork doc-loader.js 加料，而非另起炉灶。

4 · 点开待办 → openTab 照搬报表设计器

1
解析 formKey → 表单页坐标。F3 先用硬映射（一张 JS 常量表 FORM_MAP），F4 换注册表端点。得到 {nativePage, bizTable, domain, app, module, file}。
2
拼 props + workNode（与 openReportApplier 逐字同构）： 
function openTaskForm(t) {
  const f = FORM_MAP[t.formKey] || {}   // 解析表单坐标
  const props = {
    // 任务上下文（F3 新增的部分）
    mode: 'task', formKey: t.formKey, formMode: t.formMode,
    taskId: t.taskId, instanceId: t.instanceId,
    // 业务单据坐标（doc-loader 要的 readDef 字段）
    domain: f.domain, application: f.app, module: f.module, file: f.file,
    bizTable: t.bizTable, bizId: t.bizId, apiPath: f.apiPath,
    title: `${t.businessKey} · ${t.nodeName}`,
  }
  const sid = slug(`${t.instanceId}-${t.taskId}`)   // 每任务一个独立 tab
  const workNode = {
    id: `flow-task-${sid}`, type: 'workspace-node',
    caption: props.title, icon: 'workflow-tasks',
    workspace: {
      params: props,
      content:  { views:[ taskView('content',  props) ] },   // 表单
      property: { views:[ taskView('property', props) ] },  // 轨迹+意见历史
    },
  }
  openWorkNode(workNode)   // ← 5 级兜底链
}
3
表单页在 mount 读 props（ctx.props ?? ctx.host.__props），按 mode='task' 分流（§5）。
为什么每任务一个独立 tab（sid = instanceId-taskId）：对标报表应用器「每 org+period 一个 tab」——两条待办可并排打开、互不干扰状态。关掉 tab 不影响流程；办结后主动关 tab（§6）。

5 · 任务表单宿主页 portal.flow.task-form

这是 F3 的核心新页。它 = doc-loader 的载入能力 + 任务上下文 + 办结动作。第一版可 fork doc-loader.js。

5.1 mount 分流

async function mountTaskForm(ctx, view) {
  const p = ctx.props || ctx.host?.__props || {}
  if (view === 'content') {
    // ① 载业务单据（复用 doc-loader 的 meta 驱动载入）
    await loadBizDoc(p)              // readDef(p) → /api/doc/meta → setFlatData
    // ② 拉流程上下文（谁提的、走到哪、前面意见）
    const inst = await apiJson(`/api/flow/instances/${p.instanceId}`)
    // ③ 按 formMode 渲染：审阅区（只读单据）+ 审批意见栏（可写）+ 办理按钮
    return taskFormHtml(p, inst)
  }
  if (view === 'property') return trailHtml(p)   // 流程轨迹 + 意见历史
}

5.2 三态渲染（formMode 分流）

formMode单据区意见区按钮
approve（默认）只读审阅意见输入 + 同意/驳回办结（带 decision）
edit可编辑（按 formFields 限制可写列，F4 收紧）意见输入保存单据 + 办结
readonly只读无办结（纯确认，如「已知悉」）

6 · 办结动作与回流 闭合人机回路

1
点「同意」。收集意见 + 决策。若 formMode=edit 且改了单据，先 POST /api/<域>/<表>/save 存业务表。
2
办结任务（F1 已通用化的 complete）： 
POST /api/flow/tasks/${taskId}/complete
{ instanceId, variables: { lastDecision: "approve", comment: "..." } }
// 引擎 merge 变量 → 网关按 lastDecision/amount 流转 → 下一环节
3
回流：办结成功 → toast「已办结」→ 主动关闭当前 task tab → 通知待办中心刷新（该条从列表消失）。

6.1 跨页刷新：待办中心怎么知道要刷新

三条通知路径（择一或叠加）：
  • 事件广播：办结后 window.top.dispatchEvent(new CustomEvent('cmx-flow-task-done', {detail:{taskId, instanceId}}))；待办中心 mount 时监听，收到即 loadTodos()。对标 doc/dict 页用 window.dispatchEvent(CustomEvent) 的既有做法。
  • tab 激活刷新：待办中心页的 onActivate（页面契约钩子）里 loadTodos()——关掉 task tab 回到待办中心自然重查。最简，F3 首选。
  • 轮询兜底：待办中心 30s 轮询（对标 designer 的协同轮询），保证最终一致。
F3 用「onActivate 刷新 + 事件广播」双保险，轮询可选。

6.2 认领 / 转签（复用已有端点）

POST /api/flow/tasks/${taskId}/claim     { instanceId, userId }      // M4.1 已有
POST /api/flow/tasks/${taskId}/transfer  { instanceId, fromUser, toUser, reason } // M4.3 已有

待办中心的「认领」「转签」按钮直接调这两个现成端点，成功后刷新列表。F3 不新增任何任务操作端点。

7 · 审批意见留痕 F3 补一张表

意见既要驱动流转（进 variables.comment），也要按环节留痕供后续环节和审计查看。变量会被覆盖（同名 merge），不适合当历史。F3 补一张意见表。

-- migrations/…_cmx_flow_task_comment.up.sql
CREATE TABLE IF NOT EXISTS cmx_flow_task_comment (
    id           BIGINT       PRIMARY KEY,
    instance_id  VARCHAR(64)  NOT NULL,
    task_id      VARCHAR(64)  NOT NULL,
    node_bpmn_id VARCHAR(128),
    user_id      VARCHAR(64)  NOT NULL,
    decision     VARCHAR(32),                  -- approve/reject
    comment      TEXT,
    created_at   TIMESTAMPTZ NOT NULL
);
CREATE INDEX idx_flow_comment_instance ON cmx_flow_task_comment (instance_id);

complete handler 里，若 variables 带 comment/decision，顺带插一行留痕。GET /flow/instances/{id}/comments 供表单审批区展示历史意见（§5.3）。与 F1 关联表、F2 意见字段一脉相承——重数据/历史进表，变量只留当前决策。

风险对策
fork doc-loader 引入偏差F3 只加「任务上下文 + 办结 + 意见区」，载入/渲染逻辑原样保留；后续 F4 抽公共宿主时再收敛。先跑通再收敛。
