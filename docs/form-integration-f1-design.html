F1 · 数据管道打通

让「表单数据能进出流程」在不碰任何前端的前提下 curl 可验 · cmx-flow 表单集成第一阶段

纯后端引擎内核零改动curl 可验收地基阶段

F1 目标：把发起/办结两个 API 从 demo 硬编码字段改成通用变量入参，建立单据↔实例双向关联，让「表单产出的任意 JSON 能作为流程变量进出、并驱动网关流转」这件事在没有任何表单页的情况下用 curl 完整验证。这是整个集成的地基——地基不稳，上面的待办中心、表单宿主都是空中楼阁。
核实结论（已读代码）：引擎的 start_process_org(def_key, Variables, biz_key, org_id) 和 complete_task(instance_id, task_id, Variables) 早就接受任意 Variables，返回 ExecutionResult。瓶颈只在 API 层——两个 Req 结构把入参写死成了 applicant/amount/decision。F1 = 拆掉这道人为的墙 + 补一条关联线。

1 · 范围边界 F1 做什么、不做什么

✓ F1 做

  • StartReq / CompleteReq 改通用 variables: Value
  • 新增 businessKey / orgId 显式入参
  • 业务表加 process_instance_id 列（关联表方案见 §4）
  • 发起后回写关联 + 失败补偿
  • 提供 GET /flow/instances/{id}/variables 只读变量
  • 一套 curl 剧本端到端验证

✕ F1 不做（留后阶段）

  • formKey 绑定（F2）
  • 「我的待办」跨实例查询（F2）
  • 待办中心页 / 表单宿主页（F3/F4）
  • 任何前端页面
  • 审批意见留痕表（F3 带出）
  • 引擎内核逻辑（永不动）
可验收的一句话：F1 完成后，一个后端同学只用 curl 就能：起一个流程实例并塞入任意业务变量 → 该变量驱动网关走对分支 → 办结任务时再塞入决策变量 → 流程按决策流转到下一环节 → 查到「这个实例绑的是哪张业务单据」以及反向「这张单据在哪个流程实例里」。全程不需要任何 UI。

3 · 改动一：通用变量入参 拆掉 API 层的墙

3.1 新 StartReq

#[derive(Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct StartReq {
    definition_key: String,                // 必填(去掉默认 credit_approval)
    #[serde(default)]
    business_key: Option<String>,          // 人读单号 PAY-2026-0042
    #[serde(default)]
    org_id: Option<String>,               // 发起组织(驱动子流程路由)
    #[serde(default)]
    variables: Value,                      // ← 任意业务/决策变量对象
    // F1 可选：发起即绑单据(见 §4)
    #[serde(default)]
    biz_link: Option<BizLink>,           // { bizTable, bizId }
}

pub async fn start_instance(…, Json(req): Json<StartReq>)
      -> Result<Json<ApiResp<Value>>> {
    let vars = Variables::from_json(req.variables);   // 一行喂进引擎
    let result = rt.engine
        .start_process_org(&req.definition_key, vars,
                            req.business_key, req.org_id).await?;
    // F1 §4：若带 biz_link，回写关联(带补偿)
    if let Some(link) = req.biz_link {
        link_biz_to_instance(&link, &result.instance_id).await?;
    }
    load_view(rt, &result.instance_id).await
}
兼容性注意：现有 demo 前端（cmx-flow-demo）和已落地的设计工作台可能还在发老形状的 {applicant, amount}。两种处理：(a) 保留一个 #[serde(default)] applicant/amount 的向后兼容层，若 variables 为空则从旧字段拼一个（渐进迁移）；(b) demo 是独立 crate，直接改它的调用。建议 (a)——一个 fn legacy_vars(req) -> Value 兼容垫片，零破坏，后续删除。

3.2 新 CompleteReq

#[derive(Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct CompleteReq {
    instance_id: String,
    #[serde(default)]
    variables: Value,        // ← 办结提交的任意变量(含决策/意见)
    // 向后兼容：decision 若单独传，并入 variables.lastDecision
    #[serde(default)]
    decision: Option<String>,
}

// handler: 合并 decision 兼容旧调用
let mut vars = Variables::from_json(req.variables);
if let Some(d) = req.decision { vars.set("lastDecision", json!(d)); }
rt.engine.complete_task(&req.instance_id, &task_id, vars).await?;
为什么这样就够：网关条件表达式（如 ${amount > 50000}、${lastDecision == 'approve'}）读的就是实例变量。表单办结时把 lastDecision/amount/任意字段 塞进 variables，complete_task 一 merge，下一步网关立刻能读到。F1 不需要「表单」，只需要让 curl 能塞变量——变量塞进去了，流转就活了。

4 · 改动二：单据↔实例关联 两个方向都要能查

「这个实例绑哪张单据」和「这张单据在哪个流程里」——两个方向都要 O(1) 可查。有两种落法，F1 选关联表（解耦、不侵入业务表）。

方案 A：业务表加列 侵入

每张业务表加 process_instance_id BIGINT。

优点：单表查单据即知流程。缺点：要改每一张可走流程的业务表；一单多流程时不够用。

方案 B：独立关联表 F1 选这个

一张 cmx_flow_biz_link，多对多，业务表零改动。

优点：解耦、一单可挂多流程（如「报销单」既走审批又走付款）、双向索引。缺点：多一次 join。

4.1 关联表 DDL

-- docs/sql/migrations/20260801_001_cmx_flow_biz_link.up.sql
CREATE TABLE IF NOT EXISTS cmx_flow_biz_link (
    id             BIGINT       PRIMARY KEY,        -- 后端铸号
    instance_id    VARCHAR(64)  NOT NULL,           -- cmx_flow_instance.id
    biz_table      VARCHAR(128) NOT NULL,           -- cf_pay_request
    biz_id         VARCHAR(128) NOT NULL,           -- PR8842(单据主键,字符串兼容)
    biz_key        VARCHAR(128),                     -- 人读单号(冗余,便于展示)
    role           VARCHAR(32)  NOT NULL DEFAULT 'primary', -- 主单/附件…
    created_at     TIMESTAMPTZ NOT NULL
);
-- 双向查询索引
CREATE INDEX idx_biz_link_instance ON cmx_flow_biz_link (instance_id);
CREATE UNIQUE INDEX uq_biz_link_biz
    ON cmx_flow_biz_link (biz_table, biz_id, instance_id);

同库（fico-db）；cmx_ 前缀、无外键（软关联 + 索引）、id 后端铸号——完全对齐现有约定（对标 cmx_flow_definition 系列的落法）。

4.2 两个查询端点

端点用途
GET /api/flow/instances/{id}/biz正向：实例 → 绑的单据（表+主键+单号）
GET /api/flow/biz/{table}/{bizId}/instances反向：单据 → 关联的流程实例（含状态，可判「在审批中」）

反向端点是关键：业务单据列表页据此显示「审批中/已通过」徽标——虽然 F1 不做页面，但端点先备好，F3 直接用。

5 · 发起链路的事务与补偿 数据双写一致性

发起 = 「存业务单据 + 起流程实例 + 写关联」三步跨两个子系统（dct 存储 + flow 存储）。虽同库但非同一事务，必须设计失败补偿，否则会出现「单据存了流程没起」的孤儿。

5.1 F1 的编排选择：客户端编排 vs 服务端编排

F1 采用「服务端不强绑，客户端按序调 + 幂等兜底」。理由：起流程的动作天然发生在表单提交时（F3/F4），由前端按序调三个已存在的端点最自然；F1 只需保证每步幂等 + 提供对账端点，让偶发失败可自愈，不引入分布式事务框架。
客户端(F3表单/F1的curl脚本) 服务端 │ │ ① POST /api/dct/entries (存单据, 幂等: 同 biz_key upsert) │ ──────────────────────────────► dct 落库, 返回 {idMap: {temp→PR8842}} │ ◄────────────────────────────── │ 拿到真实 bizId = PR8842 │ │ ② POST /api/flow/instances │ { definitionKey, businessKey, orgId, │ variables:{...}, bizLink:{bizTable, bizId} } │ ──────────────────────────────► 起实例(引擎) │ + 写 cmx_flow_biz_link (§4) │ ⚠ 若 link 写失败 → 见 5.2 │ ◄────────────────────────────── │ { instanceId: inst_77, state: RUNNING, openTasks:[…] } ▼

5.2 失败补偿矩阵

失败点后果补偿
① 存单据失败无单据、无流程整体失败返回，用户重试。无残留。
② 起流程失败（单据已存）孤儿单据（无流程）单据状态默认 draft；未关联流程的 draft 单据可重新提交发起。对账端点 §4.2 反向查为空即「未进流程」。
②内 link 写失败（实例已起）孤儿实例（无单据关联）关键：link_biz_to_instance 失败时，回滚实例（调 cancel_instance）或标记实例 orphan 待对账。F1 选前者——起实例与写 link 在 handler 内顺序执行，link 失败即取消实例，对客户端表现为「发起失败，请重试」。
为什么不上分布式事务：同库（fico-db）下，起实例（save_snapshot 单事务）+ 写 link，可以放进同一个 DB 事务——若 PgRuntimeStore 暴露「在既有事务内写 link」的钩子，则实例与 link 天然原子。F1 务实做法：先用「link 失败即 cancel 实例」的应用层补偿（改动最小），把「同事务写 link」列为 F1 的加固项（若 store 事务边界允许）。单据（步骤①）与流程（步骤②）之间用幂等 + 对账，不追求跨子系统强一致——审批场景容忍「单据先落草稿、流程稍后起」。

7 · curl 验收剧本 F1 的灵魂：无 UI 全验证

用真实存在的定义 credit_approval（或造一张带金额网关的测试定义）跑通全链路：

# 0) 登录拿 token（dev 白名单也可免）
TOKEN=$(curl -s .../api/auth/login -d '{"username":"admin","password":"cmxadmin"}' | jq -r .data.access_token)

# 1) 起流程，塞任意业务变量（金额 8.5 万 → 应触发大额分支）
curl -s -X POST .../api/flow/instances -H "Authorization: Bearer $TOKEN" -d '{
  "definitionKey": "credit_approval",
  "businessKey":   "PAY-2026-0042",
  "orgId":         "d_fin_sh",
  "variables": { "amount": 85000, "applicant": "u_1001",
                 "bizTable": "cf_pay_request", "bizId": "PR8842" },
  "bizLink": { "bizTable": "cf_pay_request", "bizId": "PR8842" }
}'
# → { instanceId: "inst_77", state: "RUNNING", openTasks:[{id:"t1", nodeBpmnId:"review"}] }

# 2) 验证变量进去了
curl -s .../api/flow/instances/inst_77/variables -H "Authorization: Bearer $TOKEN"
# → { amount:85000, applicant:"u_1001", bizTable:..., bizId:... }

# 3) 验证正向关联
curl -s .../api/flow/instances/inst_77/biz -H "Authorization: Bearer $TOKEN"
# → { bizTable:"cf_pay_request", bizId:"PR8842", bizKey:"PAY-2026-0042" }

# 4) 验证反向关联
curl -s .../api/flow/biz/cf_pay_request/PR8842/instances -H "Authorization: Bearer $TOKEN"
# → [{ instanceId:"inst_77", state:"RUNNING", definitionKey:"credit_approval" }]

# 5) 办结第一个任务，塞决策变量 → 驱动流转
curl -s -X POST .../api/flow/tasks/t1/complete -H "Authorization: Bearer $TOKEN" -d '{
  "instanceId": "inst_77",
  "variables": { "lastDecision": "approve", "comment": "金额属实，同意" }
}'
# → state 推进；因 amount>5万，openTasks 出现下一环节(总监审批)

# 6) 反证：造一个 amount=3000 的实例，办结后应走小额直通/结束
#    证明"变量真的驱动了网关"，而非碰巧
验收判据：步骤 5 与步骤 6 的流转结果不同（大额多一环、小额少一环），且差异完全由 curl 塞进去的 amount/lastDecision 决定——这就证明了「表单数据（此处由 curl 模拟）能进出流程并驱动流转」。F1 达标，且没写一行前端。

8 · 单据字段回填变量 单一事实源

§7 的 curl 里 amount 是手填的。真实场景（F3）amount 来自业务单据。F1 要立好规矩：决策字段以单据为准，起流程时从单据快照取，不让人再填一遍——否则单据里 8 万、变量里填成 5 万，网关走错。

8.1 规矩：变量是单据的投影，不是副本

  • 发起时：服务端可选地从刚存的单据里读关键字段（如 amount）注入变量，而非信任客户端传的 amount。
  • F1 落法：StartReq 支持一个可选的 varsFromBiz: ["amount", "applicant"] 白名单——服务端按 bizLink 查单据、取这些字段、覆盖进 variables。客户端传的同名值仅作 fallback。
  • 不做也可（F1 最小版可让客户端传全量变量），但建议 F1 就把这个投影钩子留好，避免 F3 才发现字段漂移要返工。
取舍：F1 最小实现可以先不做 §8 的自动投影，只在文档约定「决策字段以单据为准」，把 varsFromBiz 作为 F1 的加固项 / F3 的前置项。核心 F1（§3/§4/§5/§7）不依赖它。这里列出是为了在地基阶段就锁定单一事实源原则，防止后面数据漂移。

10 · 风险 F1 特有

风险对策
破坏现有 demo/设计工作台的起流程调用兼容垫片（§3.1a）：variables 空时从旧字段拼；灰度期两形状并存，回归测试覆盖旧路径。
link 与实例非同事务 → 孤儿F1 应用层补偿（link 失败即 cancel 实例）；加固项：探 PgRuntimeStore 事务边界能否同事务写 link。
bizId 类型：单据主键是 bigint，关联表存字符串关联表 biz_id VARCHAR 兼容各种主键（bigint/code/uuid）；查询按字符串精确匹配，铸号侧保证唯一。
variables 无 schema，什么都能塞F1 不做校验（保持通用）；决策字段的约束靠 §8 单一事实源 + F2 formFields 白名单。地基阶段刻意宽松。
一单多流程（报销单既审批又付款）关联表 role 列 + 多对多设计已支持；反向查返回数组。
F1 一句话：拆掉 API 层那道把 variables 写死成 applicant/amount 的人为的墙，补一张单据↔实例关联表，让「任意业务数据能作为变量进出流程、驱动流转」这件事用 curl 就能端到端证明。引擎内核一行不动，前端一页不写。地基夯实了，F2 的 formKey 绑定、F3 的待办开表单才有稳固的立足点。
