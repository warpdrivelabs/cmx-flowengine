F2 · formKey 绑定 + 我的待办

让流程「知道」每个环节该开哪张表单 · 让办理人「看得到」跨所有实例的待办 · 仍是纯后端 + 设计器属性面板一处

定义带表单跨实例待办查询编译器同构扩展F3 的前置

F2 目标：在 F1 的数据管道之上，让流程定义携带「环节→表单」的绑定（userTask 上 cmx:formKey），并提供「我的待办」跨实例聚合端点——把散落在 N 个实例里的任务，按办理人一次查出，每条带上 formKey + 业务引用。F2 完成后，前端（F3）拿到一条待办就立即知道「点开该渲染哪张表单、绑哪张单据」，无需再逐个实例翻查。
核实结论（已读代码）：三处基础设施超预期就绪——① 编译器 local_attr(node,"…") 前缀无关取属性，加 formKey 是 3 行；② 任务表已有 idx_cmx_flow_task_open (assignee, completed) 和候选表 idx…_candidate_user (resolved_user_id)，「我的待办」查询天然走索引；③ ProcessDefinition::node_by_bpmn(id) 已存在，formKey 无需冗余进任务表——查询时按 task.node_bpmn_id 反查定义即可。

1 · 范围边界 F2 做什么、不做什么

✓ F2 做

  • UserTask IR 加 form_key/form_mode/form_fields
  • 编译器解析 cmx:formKey 等（3 行）
  • 任务外化 JSON 带 formKey/formMode/formFields（反查定义得来）
  • 新增 GET /flow/tasks/my（跨实例，含直派 + 候选未认领）
  • 表单注册表 cmx_flow_form_binding（formKey→页/表映射）
  • 设计器属性面板加「绑定表单」字段（走 $attrs）

✕ F2 不做（留后阶段）

  • 待办中心页 / 表单宿主页（F3/F4）
  • 真正「打开表单」的 openTab（F3）
  • 审批意见留痕表（F3）
  • 动态渲染表单字段（F4）
  • 引擎流转逻辑（永不动）
  • formFields 白名单的强制校验（F2 只透传，F4 才用）
可验收的一句话：F2 完成后，curl 能查到「用户 u_2001 的所有待办」，每条带 {taskId, instanceId, businessKey, nodeName, formKey:"pay.review", formMode:"approve", bizTable, bizId}；且在设计工作台里给 userTask 配的 formKey，发布后能被引擎编译、并出现在该端点返回里。前端此时只差「拿这条数据去 openTab」——那是 F3。

2.4 设计器属性面板：$attrs 读写先例

// design-workbench.js:460 —— cmx:calledKey 的现成写法(自定义命名空间属性)
function setCalledKey(el, value) {
  const b = el.businessObject
  const attrs = { ...(b.$attrs || {}) }
  if (value) attrs['cmx:calledKey'] = value
  else { delete attrs['cmx:calledKey'] }
  state.modeler.get('modeling').updateProperties(el, { $attrs: attrs })
}
关键坑（已被 calledKey 踩过）：bpmn-js 未注册 cmx: moddle 扩展，自定义属性落在 businessObject.$attrs，不是 .get('cmx:formKey')。读写都必须走 $attrs，saveXML 时才会序列化进 XML，引擎 compile 才认。formKey 完全复制 calledKey 这套 getFormKey/setFormKey。

3.1 UserTask IR 加三字段

// cmx-flow-model/src/ir.rs:119 UserTask —— 加在 cc 之后
pub struct UserTask {
    // … assignee / candidate_groups / multi_instance / candidates / cc 不动 …
    /// 绑定表单逻辑名（F2）。空 = 该环节无表单(纯审批按钮/serviceTask 风格)。

4 · 改动二：formKey 外化到任务视图 让任务 JSON 带表单信息

任务外化给前端的 JSON（instance_view 里的 tasks[]，以及 §5 的我的待办）要带 formKey。数据来源是反查定义，不是任务表新列（§7）。

4.1 组装辅助函数

// cmx-flow-api/src/views.rs 或 handlers.rs 加一个 helper
/// 按 (definition_key, node_bpmn_id) 反查该 userTask 的表单绑定。
fn form_of_task(def: &ProcessDefinition, node_bpmn_id: &str)
    -> (Option<String>, Option<String>, Vec<String>) {
    match def.node_by_bpmn(node_bpmn_id).map(|n| &n.kind) {
        Some(NodeKind::UserTask(ut)) =>
            (ut.form_key.clone(), ut.form_mode.clone(), ut.form_fields.clone()),
        _ => (None, None, vec![]),
    }
}

4.2 任务 JSON 加字段

// 现有 instance_view tasks[] 每条 json!({...}) 加：
"formKey":    form_key,
"formMode":   form_mode.unwrap_or("approve"),
"formFields": form_fields,
// bizRef 从实例变量取（F1 已把 bizTable/bizId 塞进 variables）：

5.2 查询实现（走已有索引）

-- 直派待办：走 idx_cmx_flow_task_open (assignee, completed)
SELECT t.*, i.definition_key, i.business_key, i.variables
FROM cmx_flow_task t
JOIN cmx_flow_instance i ON i.id = t.instance_id
WHERE t.assignee = $1 AND t.completed = false
  AND i.state = 'RUNNING';               -- 只活跃实例

-- 候选未认领：走 idx…_candidate_user (resolved_user_id)
SELECT t.*, i.* FROM cmx_flow_task_candidate c
JOIN cmx_flow_task t ON t.id = c.task_id AND t.completed = false
JOIN cmx_flow_instance i ON i.id = t.instance_id
WHERE c.resolved_user_id = $1 AND t.assignee IS NULL;   -- 未认领

store 层加两个查询方法 find_open_tasks_by_assignee / find_claimable_tasks_by_user，返回 (Task, InstanceLite) 元组；handler 层再对每条按 definition_key 取内存定义、反查 formKey（§4.1）组装。

5.3 formKey 反查的批处理

N+1 注意：50 条待办若逐条 node_by_bpmn 反查定义，是 50 次内存查找（不是 DB，可接受）。但定义是内存 HashMap，node_by_bpmn 是 Vec::find——若单定义节点多，可预建 (def_key, bpmn_id)→UserTask 的缓存。F2 先直接反查（内存操作，50 条无压力），列为可选优化。

7 · 关键决策：反查 vs 冗余 formKey 存哪

「任务要带 formKey，是把 formKey 冗余进任务表，还是查询时反查定义？」——这决定 schema 改不改、以及改定义后存量任务是否漂移。

方案 A：冗余进任务表 不选

令牌到 userTask 建 Task 时，把 formKey 写进任务表新列。

  • 查询快（无需反查）
  • ✕ 任务表加列 + 迁移
  • ✕ 改了定义的 formKey，存量在办任务仍是旧值（快照全删重插也不会更新已建任务的语义）
  • ✕ 会签子任务要各存一份

方案 B：查询时反查定义 F2 选这个

任务只存 node_bpmn_id（已有）；要 formKey 时 node_by_bpmn 反查内存定义。

  • 任务表零改动
  • formKey 永远跟定义走——改了绑定，所有任务立即反映
  • 反查是内存操作（定义常驻 HashMap），50 条无压力
  • 会签子任务共享同一 node，天然一致
决策：方案 B。核心理由不是省一列，而是语义正确性——formKey 是「定义属性」，不是「任务实例状态」。任务实例状态（assignee/completed/element_value）才该落任务表；formKey/formMode 属于定义，随定义版本走。反查让「表单绑定」始终是定义的单一事实源，与 F1「变量是单据投影」、版本管理「active_version 指针」一脉相承。代价——反查依赖「实例的定义仍在引擎内存」。已发布定义启动即装载；万一某历史版本未装载，降级返回 formKey=null，前端走通用只读兜底（不阻断待办打开）。

10 · 风险 F2 特有

风险对策
反查依赖定义在内存（方案 B 的软肋）已发布定义启动即装载；未装载则 formKey 降级 null，前端走通用只读兜底，待办仍可打开可办结（不阻断流程）。
会签子任务的 formKey子任务共享同一 node_bpmn_id，反查天然拿到同一 formKey；element_value（各人数据）另走 F1 变量，不影响表单绑定。
my 端点权限：能查别人的待办？assignee 参数应来自登录态（CmxSvrContext 里的当前用户），不信任 query 传值；管理员视角另开 ?onBehalf= 且校验角色。F2 先绑当前用户。
formKey 拼错/指向不存在的表单F2 只透传 formKey，不校验存在性；F3 打开时查注册表失败则通用只读兜底。设计器下拉选择（§6.3）从源头减少拼错。
转签/委派任务的归属（M4.3）my 端点按 assignee 查——委派后 assignee=代理人，天然出现在代理人待办；owner_user_id 可另作「我委派出去的」视图（F3）。
