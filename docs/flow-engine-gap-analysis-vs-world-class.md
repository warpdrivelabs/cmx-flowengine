# cmx-flowengine 对标全球优秀流程引擎 · 差距分析与补短板路线

> 在 P0–P6 能力补齐（身份/变量/条件/属性面板/子流程/退回）落地之后，对本引擎做一次**诚实、全面**的横向对标：与 Camunda 7/8(Zeebe)、Flowable、Activity、Temporal、Airflow、n8n 等业界标杆逐维度比较，找出**真实差距点**与**必须补的短板**，按优先级形成路线。
>
> **本文档只做分析，不动代码。** 版本 v1 · 2026-08-13
>
> 结论先行：**本引擎在"审批流(human-centric workflow)"这一细分赛道已达到可用且设计干净的水平，但距离"通用流程引擎"仍有系统性差距——差距不在审批功能点，而在 ①BPMN 元素覆盖 ②执行架构的伸缩性/可靠性 ③决策与规则(DMN) ④运维可观测性 ⑤生态与标准兼容。**

## 1. 对标对象与赛道定位

先厘清"全球优秀流程引擎"不是单一物种，分三条赛道，差距要分赛道谈：

| 赛道 | 代表 | 内核范式 | 本引擎相对位置 |
|---|---|---|---|
| **A. 人本审批流** | Flowable / Camunda 7 / activiti / 钉钉审批 / 飞书审批 | BPMN + 任务表 + 人工节点 | **同赛道，已可竞争，差在元素覆盖** |
| **B. 云原生编排** | Camunda 8(Zeebe) / Conductor / AWS Step Functions | 分区日志 / 状态机 / 水平扩展 | **架构范式不同，系统性落后** |
| **C. 持久化代码编排** | Temporal / Cadence / Restate | 确定性重放 / 事件溯源 / 代码即流程 | **不同物种，非直接竞品** |

> **战略判断**：本引擎应**继续深耕赛道 A（人本审批）**，把 BPMN 子集补全到"审批场景够用的完整度"，同时**有选择地吸收赛道 B 的可靠性/伸缩性做法**（幂等、恢复、水平扩展），**不盲目追赛道 C**（代码编排是另一个产品）。下文差距按此战略排序。

## 2. 差距详解（按维度）

### 2.1 🔴 BPMN 元素覆盖 —— 最大的"功能面"差距

**现状（源码实证）**：`NodeKind` 仅 8 种；编译器 `is_flow_node_like` 黑名单**显式拒绝** 13 类元素：
`task / scriptTask / businessRuleTask / sendTask / receiveTask / manualTask / subProcess / inclusiveGateway / eventBasedGateway / complexGateway / intermediateCatchEvent / intermediateThrowEvent / 非定时器 boundaryEvent`。

**Camunda/Flowable 覆盖近 100% BPMN 2.0**。差距清单：

| 缺失元素 | 审批场景是否需要 | 说明 |
|---|:--:|---|
| **inclusiveGateway（包容网关）** | ⭐⭐⭐ 高频 | 多条件分支"满足几条走几条"（如金额+类型同时触发多路会签）。审批流真实需要。 |
| **eventBasedGateway（事件网关）** | ⭐⭐ | "等审批 or 等超时，谁先到走谁"——超时自动处理的标准建模方式。 |
| **subProcess（嵌入式子流程）** | ⭐⭐⭐ | 与 callActivity 不同：同定义内的分组/事务边界/事件作用域。审批常用"会签块整体加边界超时"。 |
| **eventSubProcess（事件子流程）** | ⭐⭐ | 流程内"随时可触发"的异常处理块（如"随时撤单"）。 |
| **中间事件(catch/throw)** | ⭐⭐ | 消息等待、信号广播、中间定时等待（"等 3 天再提醒"）。 |
| **消息/信号事件** | ⭐⭐ | 跨流程通信、外部系统回调唤醒（如"等第三方审批结果"）。 |
| **错误/补偿/升级事件** | ⭐⭐ | 业务异常回滚（补偿：已打款要冲销）、逐级升级。 |
| **terminateEndEvent** | ⭐⭐ | "一票否决"立即终止全流程所有分支。 |
| **scriptTask** | ⭐ | 轻量计算节点（可被 serviceTask+delegate 替代，优先级低）。 |
| **businessRuleTask** | ⭐⭐ | 接 DMN 决策表（见 2.4）。 |

**补短板建议**（按审批 ROI 排序）：
1. **inclusiveGateway** — 编译器+引擎的 fork/join 逻辑扩展，审批分支刚需。
2. **terminateEndEvent + 中间定时事件** — 一票否决、延时提醒。
3. **嵌入式 subProcess + 边界事件作用域** — 会签块级超时/取消。
4. **消息/信号中间事件** — 外部系统回调唤醒（配合 2.7 的相关性）。

### 2.2 🔴 事件体系 —— 只有"一个半"事件

**现状**：唯一支持的事件是**边界定时器**（`timerEventDefinition` + `timeDuration`），且只能挂 userTask。startEvent/endEvent 是"裸"的（无消息启动、无终止语义）。

**世界级引擎的事件矩阵**（Camunda 为例）：

| 事件位置 × 类型 | 本引擎 | Camunda |
|---|:--:|:--:|
| Start: none/timer/message/signal/conditional/error | 仅 none | 全 |
| Intermediate catch: timer/message/signal/link/conditional | 无 | 全 |
| Intermediate throw: message/signal/escalation/link | 无 | 全 |
| Boundary: timer/message/signal/error/escalation/compensation/conditional（中断+非中断） | 仅 timer(中断+非中断已有) | 全 |
| End: none/message/signal/error/escalation/terminate/compensation | 仅 none | 全 |

**为何是"事件"而非"节点"是深层差距**：世界级引擎把事件做成**统一的订阅/相关性(correlation)机制**——消息事件靠 `correlationKey` 把外部消息路由到正确的等待实例。本引擎无消息订阅表、无相关性机制，因此"等外部系统回调唤醒流程"这类集成场景**根本无法建模**。

**补短板建议**：
1. **定时启动事件 + 中间定时事件**（复用已有 timer 基建，成本低）。
2. **消息订阅 + 相关性机制**（新增 `cmx_flow_message_subscription` 表 + correlate API）——这是打通"外部系统驱动流程"的关键基座。
3. **terminate/error/信号事件**逐步补。

---

### 2.3 🟡 网关 —— 缺包容与事件网关

**现状**：排他(exclusive)+并行(parallel)。并行 fork/join 已实现（M2），退回/驳回复用其 join 计数。

**差距**：
- **inclusiveGateway（包容）**：见 2.1，最高频缺失。
- **eventBasedGateway（事件）**：依赖 2.2 的事件体系。
- **complexGateway**：几乎无人用，可不补。

本项与 2.1/2.2 联动，一起做。

---

### 2.4 🔴 决策与规则引擎（DMN）—— 完全空白

**现状**：**无 DMN，无决策表，无规则引擎**。所有条件靠自研表达式 DSL（`eval_condition`，21 内置函数）。

**世界级现状**：Camunda/Flowable 都内置 **DMN 引擎**（Decision Model and Notation 标准）——审批场景的核心价值之一：
- **决策表(Decision Table)**：把"什么金额/什么部门 → 走什么审批路径/几级审批"做成业务可维护的表格，而非硬编码条件。
- **FEEL 表达式**（DMN 标准表达式语言）：比自研 DSL 强大且标准化。
- **DRD（决策需求图）**：多决策编排。

**差距影响**：本引擎的分支条件必须写在 BPMN 边上（P2 已做可视化构造器），但"审批矩阵"这类**业务频繁变更的决策逻辑**无法从流程定义里剥离出来独立维护——这是企业级审批平台的高频诉求（"调整审批权限矩阵不应改流程图"）。

**补短板建议**：
1. **轻量决策表**（不必全 DMN）：新增 `metaKind:DMN` 或决策表元模型 + 一个 `evaluateDecision(table, inputs) → outputs` 引擎，businessRuleTask 调它。可复用已有 cmx-dct 字典/元模型基建。
2. 长期：向 **FEEL 子集**靠拢（表达式标准化）。

### 2.5 🔴 执行架构 —— 单实例轮询 vs 分区流式（最深的架构差距）

**现状（源码实证）**：
- 引擎是**进程内单例**（OnceCell-per-tenant），token 执行 `run_to_wait` 同步跑到等待态。
- 定时器靠 **5 秒 tokio interval 轮询** `find_due_jobs`（已有 SKIP LOCKED 做多实例 HA，这点不错）。
- 每个等待点 = 一次 `save_snapshot` 事务（整实例快照重写）。

**世界级现状**：

| 维度 | 本引擎 | Camunda 7 | **Zeebe (Camunda 8)** | Temporal |
|---|---|---|---|---|
| 执行模型 | 内存单例 + 同步推进 | DB 悲观锁 + job executor | **分区 Raft 日志 + 流式处理** | **分片 + 确定性重放** |
| 水平扩展 | ❌ 单进程（多实例仅抢占定时器） | 有限（DB 争用） | ✅ 分区线性扩展 | ✅ 分片百万级 |
| 吞吐 | 低（适合审批量级） | 中 | **高（十万+/s）** | 极高 |
| 背压 | ❌ | ❌ | ✅ | ✅ |
| 故障恢复 | 快照重载（重启装载已发布定义） | DB 恢复 | **日志重放** | **事件溯源重放** |
| 大实例 | 整快照重写（大流程慢） | 增量 | 增量 | 增量 |

**关键差距点**：
1. **无异步 job executor / 工作队列**：serviceTask/delegate 是同步执行的，一个慢外部调用会阻塞 `run_to_wait`。世界级引擎把外部任务丢进**异步 job 队列**（Zeebe 的 job worker 模型）。
2. **整快照事务**：`save_snapshot` 每次重写整个实例的 tokens/tasks。**大流程（几百节点/会签几百人）会成为性能瓶颈**。世界级引擎是增量持久化。
3. **无水平扩展的执行**：单进程执行 token（多实例只抢定时器）。审批量级够用，但不是"世界级伸缩"。
4. **热装载缺口**（已知）：发布新定义需重启引擎才装载——`load_published` 只在 boot 跑。生产不可接受。

**补短板建议**（按 ROI）：
1. **热装载**（P4 遗留）：发布后引擎立即 deploy 新版，不重启。**必做，成本低**。
2. **异步 job executor**：serviceTask 丢队列异步执行 + 重试/退避，不阻塞主推进。**审批集成刚需**。
3. **增量持久化**：save_snapshot 改成"只写变更的 token/task"，而非整实例重写。**中等成本，大流程收益大**。
4. 水平扩展执行：**暂不追**（审批量级单进程够用，投入产出比低）。

### 2.6 🔴 可靠性与执行语义

**现状**：
- 一致性靠**单事务 save_snapshot**（一个等待点一次提交）——这点是对的。
- **serviceTask 无重试/无退避/无死信**：delegate 执行失败即报错，无自动重试、无 incident（异常挂起）机制。
- **无补偿**（cancel_process 注释明说"不回滚已执行的 serviceTask 副作用"）。
- **无幂等键**：外部重复调用可能重复推进。

**世界级现状**：
- **Incident（异常事件）机制**：Camunda/Zeebe 在 job 失败耗尽重试后创建 incident，流程**挂起等人工处理**而非丢失——这是生产运维的核心。本引擎**无此机制**（失败即错误返回，实例状态未定义处理）。
- **重试策略**：可配 job 重试次数 + 退避。
- **补偿(compensation)**：BPMN 补偿事件回滚已完成活动。
- **确定性重放**（Temporal）：本引擎不追。

**补短板建议**：
1. **Incident 机制**（🔴 必做）：serviceTask/delegate 失败 → 重试耗尽 → 建 incident + 实例挂起 + 运维台可见可重试。这是**生产可用性的硬门槛**。
2. **job 重试 + 退避**：配合 2.5 的异步 job executor。
3. **补偿边界事件**：审批"已打款需冲销"场景，中优先级。

### 2.7 🟡 持久化模型与历史/审计

**现状**：11 张 `cmx_flow_*` 表 + `fid_*`(身份) + 2 历史表（`hi_instance` / `hi_task`）。审批台账（transfer/delegate/reject）落 `cmx_flow_task_delegation`。

**差距**：
- **历史粒度浅**：仅实例级+任务级历史。缺**变量历史**（谁在何时改了什么变量）、**活动实例历史**（每个节点的进出时刻，用于耗时分析/审计回放）、**决策历史**。
- **无审计日志标准**：世界级引擎有完整的 audit trail（对齐合规要求）。
- **无历史数据生命周期**：无 TTL/归档/清理策略（历史表会无限增长）。

**补短板建议**：
1. **活动实例历史表**（`hi_activity`）：记每个节点进出时刻——**驱动 2.10 的耗时/瓶颈分析 + 审计回放**。
2. **变量历史**：审计合规刚需。
3. 历史 TTL/归档策略。

---

### 2.8 🟡 表达式与脚本

**现状**：自研 DSL（P2 扩展后：嵌套路径 + 21 内置函数 + 无副作用），刻意不引 rhai/脚本引擎。

**差距**：
- **无脚本任务语言**：Camunda 支持 Groovy/JS/Python/FEEL 写 scriptTask；本引擎 scriptTask 直接被拒。
- **表达式能力弱于 FEEL/JUEL**：无日期运算（刻意，因 Clock 注入）、无集合推导（filter/map/every/some）、无区间。
- **无 FEEL 标准兼容**：跨引擎迁移不便。

**判断**：自研 DSL 的"受控、可静态校验、无沙箱风险"是**优点**（对审批安全友好），不必盲目引脚本引擎。但应：
1. 补**日期/集合类函数**（经 Clock 注入时间通道，见 P2 已留的注释）。
2. 长期考虑 **FEEL 子集**（标准化，利于 DMN）。

---

### 2.9 🟢→🟡 可视化设计器

**现状（强项）**：bpmn-js 四区工作台 + P3 专业属性面板（办理人/审批方式/超时/抄送分页签 + IAM 联动选择器）+ P2 条件可视化构造器 + 组织路由矩阵 + P5 变量映射 + P4 导入导出。**这一维度已接近世界级 human-workflow 设计器**。

**残余差距**：
- **仅支持引擎支持的元素**：palette 未做"引擎不支持元素灰化"（用户可能画出编译不过的图）——P4 曾列未做。
- **无流程模拟/调试**：Camunda Modeler 有 token 模拟。
- **无协作编辑**：多人同时编辑（cmx-rpt 有 oplog 协同先例，可借鉴）。
- **无流程图对比(diff)**：版本间可视化 diff（P4 列未做）。
- **移动端/审批 App**：世界级有原生审批 App，本引擎仅 Web。

---

### 2.10 🟡 运维与可观测性

**现状**：flow-server 根路径监控大盘（实例/待办/定义/协作聚合）+ 通用 `/_mon` 技术监控（系统/DB池/请求遥测）+ SSE 事件流 + webhook 双发。

**差距 vs Camunda Operate/Cockpit**：
- **无实例运维台**：Operate 可查单实例的 token 位置、变量、增量历史、卡在哪、为何卡；可**单实例干预**（改变量、跳节点、重试 incident、批量操作）。本引擎有 cancel/reject 但**无统一运维视图**。
- **无 incident 视图**（依赖 2.6）。
- **无节点级耗时热力/瓶颈分析**（依赖 2.7 的活动历史）。
- **无 SLA/超时看板**：哪些任务将超时/已超时。
- **无批量操作**：批量改派/批量取消/批量迁移。

**补短板建议**：
1. **单实例运维视图**（token 位置 + 变量 + 历史时间线 + 卡点诊断）——运维刚需。
2. **incident 台**（配合 2.6）。
3. 节点耗时热力（配合 2.7）。

---

### 2.11 🟡 版本管理与实例迁移

**现状**：定义版本化（发布 version+1）+ 草稿/发布分离 + 实例绑定发起时版本（旧实例按旧定义跑完）。

**差距**：
- **无实例迁移(migration)**：Camunda/Zeebe 可把在跑的旧版实例**迁移到新版定义**（映射节点）。本引擎旧实例只能按旧版跑完——**改流程无法应用到存量实例**，长周期审批（如年度合同）痛点。
- **无版本 diff**（P4 列未做）。
- **无灰度发布**：新版只对部分实例生效。

**补短板建议**：实例迁移是中长期能力，审批场景可**先做"节点映射迁移"最小版**（把卡在 A 节点的旧实例迁到新版 A'）。

---

### 2.12 🔴 生态与连接器

**现状**：一个 `HttpDelegate`（serviceTask 走 HTTP）+ webhook 出站 + SSE。

**差距**：Camunda/Zeebe 有**连接器市场**（上百个开箱即用连接器：REST/gRPC/Kafka/邮件/Slack/数据库/AWS/GPT…）+ SDK（多语言 job worker）。本引擎**无连接器生态、无外部 job worker SDK**。

**补短板建议**：
1. **连接器抽象层**：把 delegate 从"注册表键"升级为"可配置连接器"（REST/邮件/消息队列/webhook 几个内置）。
2. **外部 job worker 协议**：让外部服务能拉取并完成 serviceTask（对齐 Zeebe job worker 范式）——配合 2.5 的异步 job executor。

---

### 2.13 🟡 测试、契约与标准兼容

**现状**：~155 测试（Rust 单测 + PG 集成 + VM 纯函数 + CDP 真机），可注入 Clock 做定时器测试。

**差距**：
- **无 BPMN 标准符合性测试**：能否跑标准 BPMN TCK（技术兼容性套件）？本引擎是子集，标准图导入会被拒。
- **无流程测试 DSL**：Camunda 有 `bpmn-assert`/Zeebe test。本引擎测试是手写引擎调用。
- **无时间跳跃测试框架**（Temporal 强项）：虽有 Clock 注入，但无高层测试 API。

## 3. 差距归类：三张"必须补"清单

### 3.1 🔴 P级：生产可用性硬门槛（不补则不能上生产）

| # | 短板 | 为什么是硬门槛 | 关联维度 |
|---|---|---|---|
| H1 | **定义热装载** | 发布新版需重启引擎——生产不可接受 | 2.5 |
| H2 | **Incident 机制 + job 重试** | serviceTask 失败即丢/报错，无人工兜底——数据/流程会卡死或丢失 | 2.6 |
| H3 | **异步 job executor** | 同步执行外部调用会阻塞整个引擎推进 | 2.5 |
| H4 | **单实例运维视图** | 出问题无法诊断"卡在哪、为什么"——运维盲区 | 2.10 |

### 3.2 🟡 A级：审批赛道竞争力（补了才算"完整的审批引擎"）

| # | 短板 | 审批场景价值 | 关联维度 |
|---|---|---|---|
| A1 | **inclusiveGateway（包容网关）** | 多条件并行审批分支，高频 | 2.1/2.3 |
| A2 | **terminateEndEvent（一票否决）** | 否决立即终止全流程 | 2.1 |
| A3 | **轻量决策表(DMN子集)** | 审批矩阵业务可维护，不改流程图 | 2.4 |
| A4 | **消息事件 + 相关性** | 外部系统回调唤醒流程 | 2.2 |
| A5 | **嵌入式 subProcess + 块级边界超时** | 会签块整体超时/取消 | 2.1 |
| A6 | **活动历史 + 耗时分析** | 审批效率分析、审计回放、SLA | 2.7/2.10 |
| A7 | **P6 剩余动作**：取回/自由跳转/挂起恢复/催办 | 审批高频运营动作 | (P6续) |

### 3.3 🟢 B级：世界级完整度（长期，投产报比择机）

| # | 短板 | 说明 |
|---|---|---|
| B1 | 实例迁移(migration) | 改流程应用到存量实例 |

| B7 | 变量历史 + 历史 TTL/归档 | 审计合规 + 数据治理 |

## 4. 建议路线（在 P0–P6 之上的"下一程"）

分三个里程碑，**先补生产硬门槛，再补审批竞争力，最后择机追世界级完整度**：

### 里程碑 Q1：生产化（H1–H4）
> 目标：从"功能可用"到"生产可上"。
- 定义热装载（发布即生效）
- 异步 job executor（工作队列 + 重试/退避）
- Incident 机制（失败挂起 + 运维可重试）
- 单实例运维视图（token/变量/历史/卡点诊断）

### 里程碑 Q2：审批赛道完整（A1–A7）
> 目标：成为"BPMN 审批子集的完整引擎"。
- inclusiveGateway + terminateEndEvent（编译器+引擎）
- 轻量决策表（复用 cmx-dct 元模型）
- 消息事件 + 相关性机制（打通外部回调）
- 嵌入式 subProcess + 块级边界事件
- 活动历史表 + 耗时/SLA 看板
- P6 剩余动作（取回/跳转/挂起/催办）

### 里程碑 Q3+：世界级完整度（B1–B8，择机）
> 目标：向 Camunda/Flowable 完整度靠拢。
- 实例迁移、补偿事件、连接器生态、全事件体系、FEEL、设计器进阶。

## 5. 诚实的结论

**本引擎不是"玩具"，但也还不是"世界级通用引擎"。**

- **强项真实**：审批人性化能力（会签/或签/加签/转办/委派/抄送/退回/关系型审批人/身份双模）+ 干净的四区可视化设计器 + 独立微服务/多租户架构 + "设计器产物=引擎输入"的契约纪律——**这些在国产审批平台里已属上乘**，对标 Flowable 人本层不落下风。

- **差距系统性**：不在"审批功能点"，而在**通用引擎的三块地基**——① BPMN 元素/事件覆盖（子集 vs 全集）② 执行架构的可靠性与伸缩性（同步单例+轮询 vs 异步分区+incident）③ 决策(DMN)与生态(连接器)。

- **战略取舍**：**不必追 Zeebe/Temporal 的云原生高吞吐**（审批量级用不上，投产报比低）；**应优先补"生产硬门槛"（热装载/异步job/incident/运维台）**，让现有能力真正可上生产；**再补"审批赛道完整度"（包容网关/决策表/消息事件/活动历史）**，坐稳赛道 A 头部。

一句话：**把"审批引擎"做到极致完整 + 生产级可靠，比追"通用引擎"的元素大而全更符合本引擎的定位与 ROI。**
