定位与设计哲学

设计器不是画图工具，是引擎定义的可视化编辑器。一条铁律贯穿全案。

铁律：设计器产物 = 引擎输入。 设计器最终吐出的必须是后端 cmx_flow_bpmn::compile(xml) → ProcessDefinition 能吃的 BPMN 2.0 XML。画布上画不出引擎跑不了的东西，引擎能跑的每个能力画布都能配。二者共用同一份「能力清单」，任何一端加能力，另一端同步——这是全案最重要的约束。

四条原则

原则含义
标准优先画布用 bpmn-js（bpmn.io 官方，BPMN 2.0 事实标准）。连线、撞态、缩放、对齐、撤销、导出 XML 这些底层能力免费拿，我们只做 cmx 特有的属性面板与后端打通。不自研画布引擎。
契约驱动设计器可配的属性 ⊆ 编译器可解析的属性。编译器现认 userTask 的 assignee/candidateUsers/candidateGroups/cc、callActivity 的 calledElement/cmx:calledKey/in/out、multiInstance、boundaryEvent 定时器等——属性面板逐项对标。
复用既有角色/岗位/组织选择器直接拉 IAM 表（cmx_role/cmx_position/cmx_org）；表单绑定接 cmx-form/DOC/DCT 元数据；UI 用 cmx-data-comp + UI5；工作台用 native-pages 四区范式（对标 RPT 设计器）。不重造任何一个。
专业健壮校验前置（画布实时诊断 + 保存前编译校验 + 后端 topology 校验三道闸）；定义带版本；草稿/发布分离；每步可撤销。达到「专业、精致、稳定、健壮」。

现状盘点：有什么、缺什么

动手前先照镜子。引擎侧能力已厚，前端侧从零起步，中间缺一个「定义持久化层」。

✓ 已具备（直接复用）

  • 编译器：8 种 task + 5 种 gateway + 事件 + callActivity + multiInstance + 候选人/抄送/组织路由，全能解析
  • 4 个扩展点：JavaDelegate / Clock / AssigneeResolver / SubflowRouter
  • IAM 绑定：role()/position()/org() → 真实用户，PgIamAssigneeResolver 已落地
  • 组织路由：cmx_flow_subflow_binding + 沿 path 继承
  • 表单/元数据：cmx-form、DOC/DCT 元模型、cmx-data-comp 组件库
  • 工作台范式：RPT native-pages 四区设计器（designer.js 134KB 先例）

✗ 缺口（本案要补）

  • 可编辑画布：现在只有只读 buildFlowStrip（泳道条），无拖拽设计
  • 定义持久化：engine.deploy() 只存内存 HashMap，demo 靠 include_str! 硬编码 → 设计器要能存/取/版本化定义
  • 属性面板：把 BPMN 元素的 cmx 扩展属性做成可视化表单
  • 绑定选择器：角色/岗位/组织/表单的可视化选择控件
  • 子流程组织路由 UI：calledKey → 各组织绑定的可视化矩阵
  • 部署编排：草稿 → 校验 → 发布 → 引擎装载的前端流程
最关键的缺口是「定义持久化层」。 它是设计器与引擎之间缺失的一环：设计器存 BPMN XML + 版本 → 引擎启动/热更时从库里读定义 deploy。没有它，设计器画完无处可存、引擎也读不到。阶段 0 先补这个后端基座（见第 6 节）。
3

整体架构：五层

从画布到引擎，数据只有一种流向；BPMN XML 是贯穿全链的唯一交换格式。

画布 bpmn-js→ 属性面板→ BPMN XML→ 定义服务→ compile()→ 引擎
1
画布层 bpmn-js
bpmn.io 官方渲染器。拖拽建节点、连线、对齐、缩放、撤销、导入/导出标准 BPMN XML。我们扩展它的 palette（只保留引擎支持的元素）与 renderer（cmx 图标/配色）。不碰它的核心，只加插件。
2
属性层 cmx-data-comp + UI5
选中元素 → 右侧属性面板出对应表单。userTask 出「办理人/候选人/抄送/表单/会签」；callActivity 出「子流程/组织路由」；boundaryEvent 出「定时器」。面板改动 ↔ 双向绑定到 bpmn-js 的 moddle（XML 模型）。用 CmxFloatingDialog/cmx-ui5-form/cmx-dict-select 等既有封装。
3
绑定层 IAM / 表单 / 组织
属性面板里的「选角色/选岗位/选组织/选表单」控件，实时查后端既有系统：/api/iam/roles、/api/iam/positions、/api/org/tree、/api/forms。选中的 code/id 写回 BPMN 扩展属性（flowable:candidateGroups="role(FINANCE)"）。
4
定义服务层 新建 · 阶段 0
缺口所在。cmx-flow-def 存 BPMN XML + 版本 + 状态（草稿/已发布）。CRUD + 校验（调 compile 试编译）+ 发布（version+1，引擎热装载）+ 组织路由绑定管理。存 cmx_flow_definition / cmx_flow_definition_version 表。
5
引擎层 已具备 · 契约不变
compile(xml) → ProcessDefinition + engine.deploy()。设计器不改引擎，只通过标准 BPMN XML 喂给它。引擎新增的只是「从定义服务读 XML 而非 include_str!」这一条装载路径。
为什么这个分层稳： 每层只认下一层的一种输入。画布只吐 XML，定义服务只存 XML，引擎只吃 XML。任何一层可独立替换（哪天换掉 bpmn-js，只要还吐标准 XML，后面全不动）。BPMN XML 作为「窄腰」把前后端彻底解耦。
4

四区工作台布局

对标 RPT 设计器（native-pages 四区范式），流程设计器同构：探索区 + 画布区 + 属性区 + 工具条。

◧ 探索区（左）

流程定义树 + 元素面板。

  • 已有流程列表（草稿/已发布，按模块分组）
  • BPMN 元素调色板（只列引擎支持的：开始/结束、用户任务、网关、子流程、定时边界…）
  • 拖元素到画布 / 点流程进画布编辑

▦ 画布区（中）bpmn-js

核心。bpmn-js 渲染的可交互 BPMN 图。

  • 拖拽建节点、拉线连接、框选、对齐吸附
  • 子流程节点可「钻入」看内部路径（复用现有递归渲染思路）
  • 实时诊断：断头节点、无出口网关标红

▤ 属性区（右）

选中元素的上下文属性表单。

  • 通用：id / 名称 / 文档注释
  • userTask：办理人·候选人·抄送·表单·会签
  • callActivity：子流程 key·组织路由·变量映射
  • gateway：条件表达式；boundary：定时器

▭ 工具条（顶）

命令区。

  • 保存草稿 / 校验 / 发布 / 版本历史
  • 撤销·重做（bpmn-js 原生 commandStack）
  • 缩放·适应·导入 XML·导出 XML/SVG
  • 组织路由矩阵（子流程绑定专用弹窗）
复用 RPT 范式的收益： native-pages 注册机制、四区 splitter 布局、工具条组件、explorer 树、属性面板骨架，RPT 设计器全都趟过一遍（见记忆 rpt-designer-mode / rpt-spreadjs-designer-toolbar）。流程设计器换掉中间画布（SpreadJS→bpmn-js）、换掉属性面板内容（报表元素→流程元素），骨架同构，工作量集中在画布集成与属性面板。

阶段 0：定义持久化基座

前端动工前，先补引擎侧唯一缺口。这是纯后端小切口，让「定义能存能取能版本化」。

新增 crate：cmx-flow-def

与现有 cmx-flow-model/engine/store-pg 平级。职责单一：流程定义的 CRUD + 版本 + 发布。

能力说明
save_draft(key, xml)存草稿。先调 compile(xml) 试编译，语法/拓扑错直接挡回，带结构化诊断。
publish(key)草稿 → 发布：version+1，标记 active，触发引擎热装载。旧版本保留（历史实例仍按旧版跑）。
list / get / get_version列表、取当前版本 XML、取指定历史版本。
binding CRUD组织路由矩阵的增删改查（cmx_flow_subflow_binding，M5.2 表已建）。

两张新表

-- 定义主表（当前指针）
cmx_flow_definition(
  key PK, name, module, category,
  active_version INT,           -- 指向当前发布版本
  state,                        -- DRAFT / PUBLISHED
  updated_at, updated_by )

-- 版本表（不可变历史，每次发布追加一行）
cmx_flow_definition_version(
  id PK, def_key, version INT,
  bpmn_xml TEXT,               -- 设计器产物，原样存
  published_at, published_by,
  UNIQUE(def_key, version) )
为什么存 XML 而非编译后的 IR： XML 是标准交换格式，设计器能重新加载编辑、可人工审阅、可版本 diff、可导出迁移。IR 是引擎内部结构，会随代码演进。存 XML + 装载时 compile，既保留可编辑性又保证与引擎同步。代价是每次装载编译一次——定义数量级极小（几十上百个），可忽略。

引擎装载路径改造（唯一改动）

现在：include_str!("credit.bpmn") → compile → deploy（硬编码）。
改后：def_service.list_published() → 逐个 compile → deploy（从库读）。demo 的 include_str 保留作 seed，生产走库。引擎核心零改动。

7

分阶段交付

六个阶段，每个都能独立验收、独立见效。先打通「能画能存能跑」的最小闭环，再逐步加专业设置。

阶段 0

定义持久化基座 纯后端

cmx-flow-def crate + 两张表 + 引擎从库装载。设计器的「存/取/发布」有了着落。可独立测试：存 XML → 发布 → 引擎跑起来。

阶段 1

画布最小闭环 bpmn-js

集成 bpmn-js 到 native-pages 四区工作台。能拖节点、连线、导出标准 BPMN、存草稿、发布 → 引擎能跑最简单的「开始→用户任务→结束」。打通端到端。

阶段 2

属性面板 · 基础 属性

选中元素出属性面板：id/名称/文档、办理人、网关条件、结束事件。moddle 双向绑定跑通。cmx 命名空间 moddle 扩展注册。

阶段 3

IAM 绑定 · 角色/岗位/组织 绑定

候选人选择器接 IAM：可视化选角色/岗位/组织，写回 role()/position()/org() 表达式。抄送同理。这是「人与组织」维度的可视化。

阶段 4

子流程 · 组织路由矩阵 M5

callActivity 属性面板 + 组织路由矩阵弹窗。逻辑 key、变量映射、各组织绑定不同子流程。你最关注的能力，完整可视化。

阶段 5

进阶 · 会签/定时器/表单/版本 专业

会签配置、边界定时器、表单绑定（需编译器补 formKey）、版本历史与 diff、发布审计。收尾成「专业、精致、稳定、健壮」。

阶段 1 是关键里程碑。 它证明「画布 → XML → 定义服务 → compile → 引擎」整条链通。此后每阶段都是在通路上加设置项，风险可控、增量见效。建议阶段 0+1 先做，看到端到端效果后再决定后续节奏——和 flow 引擎 M1→M5 一样的打法。
8

专业·精致·稳定·健壮 怎么落实

你的四个形容词，逐条对应到具体机制，不是口号。

专业

  • bpmn-js = BPMN 2.0 官方标准，符号/语义与 Flowable/Camunda 一致，行业通用
  • 属性面板术语对齐 BPMN 规范（会签/或签/边界事件/补偿）
  • 导出标准 XML，可被任何 BPMN 工具打开

精致

  • 沿用项目设计语言（cmx-data-comp + UI5，与 RPT 设计器同款皮肤）
  • 子流程可钻入、组织路由矩阵可视化、实时诊断高亮
  • 撤销/重做/对齐吸附/缩放适应，交互顺滑

稳定

  • bpmn-js 千万级装机量的成熟库，不自研画布核心
  • BPMN XML 窄腰解耦，前后端可独立演进
  • 定义版本化：发新版不影响在跑的旧实例
  • 草稿/发布分离，未发布不影响生产

健壮

  • 三道校验闸：画布实时诊断 → 保存前 compile 试编译 → 后端 check_topology
  • 结构化诊断（复用 CmxErrCode + 专业对话框，见记忆 dct-doc-column-validation）
  • 存 XML 原样，可回滚可审计
三道校验闸详解： ① 画布层——bpmn-js 实时标红断头节点/无条件分支；② 保存层——存草稿前后端调 compile(xml)，语法错/拓扑错（无 start、死循环、网关无出口）挡回并高亮定位；③ 装载层——发布时 check_topology 终检。一个非法流程根本存不进库，更进不了引擎。这是「健壮」的硬保证。
