cmx-flow → 独立流程微服务 v2

纯流程引擎微服务：身份/组织/表单全外部化，前端一芯三壳（门户内嵌 · 可嵌组件 · headless API 供三方自建）。

架构方案 v2 不动代码 · 纯设计 身份/组织/表单 = 外部 引擎自持
v2 相对 v1 的三处关键调整（按最新要求）：
  1. 身份/组织/表单彻底外部化 —— 流程不自带也不复制用户/角色/组织/表单，全部由第三方系统提供服务或数据。流程只持有"流程本身"的东西（定义、实例、令牌、任务、意见、抄送、绑定）。三个既有 trait（AssigneeResolver/SubflowRouter/表单绑定）从"接平台 IAM"改为接外部 HTTP 适配器。
  2. 前端"一芯三壳" —— 同一套流程 UI 逻辑，三种交付：①继续以 native_pages 内嵌 CMXPortalManager 门户（现状保留）；②抽成框架无关可嵌 Web Component（<flow-designer>/<flow-todo>/<flow-task-form>）供三方系统集成；③提供headless REST/gRPC API，三方完全自研设计器/待办界面。
  3. 集成契约已有先例 —— 平台 dev-local.toml 的 [center_client.urls] flow = "http://flow-center:8080/api/plugin/flow/import" + flow_service 服务发现早已为"外部 flow-center 服务"预留（与 menu/perm/form center 同构）。本方案正是兑现它。

1. 边界重划：流程"自持"什么，"外借"什么 v2 的核心决策

✅ 流程自持（引擎的本体，落自己的库）
  • 流程定义（BPMN + 版本 + 草稿/发布）
  • 运行态：实例 · 令牌 · 任务 · 定时器作业
  • 历史：hi_task · 意见留痕 · 抄送记录
  • 候选池（任务↔候选用户 id 快照，仅存 id）
  • 子流程组织绑定（called_key + org_id → 目标 key，仅存 id/key）
  • 表单绑定（formKey → 外部表单坐标/URL，仅存指针）
🟣 外借（第三方系统提供，流程只存 id/引用）
  • 用户（是谁、昵称、状态）——外部 IdP/HR
  • 角色/岗位（role/position → 用户）——外部
  • 组织（org 树、部门归属、path 继承）——外部
  • 表单（渲染什么、字段、数据）——外部表单系统
  • 业务单据（真实单据数据、回写）——外部业务系统
判定标准（一条线）：凡是"流程为了推进而必须知道的事实"——谁在哪个节点、令牌到哪了、任务归谁——流程自持；凡是"关于人/组织/表单的真相"——这个 id 对应谁、这个角色下有哪些人、这张表单长什么样——流程只存引用（id/key/URL），运行时向外部要。流程库里永远不会出现一张 user/role/org/form 表。
今天与目标的差：现在 PgIamAssigneeResolver（store-pg/resolver.rs）直连平台 IAM 库查 cmx_user/cmx_role/cmx_user_role/cmx_position/cmx_org。v2 把这个"直连 SQL"换成"调外部 HTTP API"——AssigneeResolver trait 一字不改（model/resolver.rs 早已中立，注释即写"引擎不依赖任何 IAM/DB"），只是换一个 HttpAssigneeResolver 实现。这是 v2 全部外部化的同一个套路：trait 不动，换实现。

3. 后端：可依赖 cmx-container 公共库 v2 放宽：允许保留 infra 依赖

v2 明确允许流程微服务依赖 cmx-container 的部分公共库（不再追求"零 cmx 依赖"）。这让后端几乎零重写——只有 cmx-flow-api 的 HTTP 装配层要脱 cmx-api（因为它拖入整个平台且带门户 CmxAppState）。infra 层（cmx-database-pg/cmx-core/cmx-job-core）大方保留。
crate层v2 动作
cmx-flow-model / bpmn / engine引擎核原样 已框架无关
cmx-flow-def / store-pg持久化原样（store-pg 的 PgIamAssigneeResolver/PgSubflowRouter 不删，作为"回连平台库"的可选实现；新增 HTTP 实现平行存在）
cmx-database-pginfra依赖 tokio-postgres 多数据源池（租户库靠它 register）
cmx-coreinfra依赖 DataValue
cmx-job-coreinfra依赖 异步作业 SSE + SKIP LOCKED 抢占（定时器/催办/webhook 重试）
cmx-flow-api → flow-httpHTTP重写装配 脱 cmx-api；handler 体逐字搬
新增 cmx-flow-adapters适配器新 crate 四个 HTTP 外部适配器（见 §4）
为什么只有 flow-api 要动：它 impl ModuleRoutes<CmxAppState> + handler 带 State(_s)/CmxSvrContext(_ctx)（绑定但基本不用）。cmx-api 传递拖入 biz/metadata/plugin/ai/portal/rpc 整个平台。重写=①自建 AppState{rt, adapters, tenant_cfg}；②自写 TenantCtx extractor；③自定义响应封套 {code,msg,data}（形状照抄，前端零改）；④普通 Router::new().route(...)。cmx-flow-demo/main.rs 已是这个形状的活样板。

4. 外部化四个适配器 身份 · 组织 · 表单 · 单据

核心手法统一：trait 保留 → 新增 HTTP 实现 → 引擎注入。每个适配器都给"外部 REST"默认实现 + "回连平台"可选实现。

① 身份适配器 —— AssigneeResolver（trait 已在，零改）

trait（model/resolver.rs:32）把 CandidateRef(user/role/position/org) 解析成用户 id 列表。今天 PgIamAssigneeResolver 查平台库。v2 新增： 
struct HttpAssigneeResolver { base_url, http, token }
// 外部身份服务约定 4 个只读端点（或合成 1 个 resolve）：
GET  {base}/identity/role/{code}/users      // role → [user_id]
GET  {base}/identity/position/{code}/users  // position → [user_id]
GET  {base}/identity/org/{id}/users?deep=1  // org 子树 → [user_id]
POST {base}/identity/resolve  {refs:[...]}   // 批量一发（推荐，省 N 次往返）
引擎 engine.set_resolver(Arc::new(HttpAssigneeResolver::new(...)))——一行切换。候选池只落 解析出的用户 id 快照，流程不存"角色→人"关系（那是外部的真相）。

② 组织适配器 —— SubflowRouter + 用户展示名

SubflowRouter（model/subflow.rs:35）按 (called_key, org_id) 解析子流程，今天沿 cmx_org.path 前缀继承。v2：组织绑定仍自持（called_key+org_id→target_key 是流程配置），但org 树/path 继承向外部组织服务查： 
GET {base}/org/{id}/ancestors   // 返回祖先链，供"沿组织树向上找绑定"
GET {base}/users?ids=a,b,c       // id → 昵称/头像/状态，纯展示（待办列表显示人名）
HttpSubflowRouter 拿祖先链在自持的绑定表里匹配。用户展示名是纯 UI 增强（前端把 id 换成名字），可缓存、可降级为显示 id。

③ 表单适配器 —— 表单绑定升级（已有 kind 分派，加 external 型）

今天表单绑定（cmx_flow_form_binding）已支持多 kind：native/html/workspace（门户页）。v2 加两个外部型，让表单完全由第三方渲染：
kind含义前端行为
external_url外部表单页 URL（模板带 {taskId}{instanceId}{formKey}{bizId}）iframe 内嵌 或 新窗口打开第三方表单
schema外部返回 JSON-Schema，流程内建轻量渲染器画表单GET {formSvc}/form/{formKey}?ctx=… 取 schema+data，提交回 PUT
native/html/workspace门户内嵌（现状）仅门户壳可用；三方壳忽略或降级
流程只存指针（URL 模板 或 formSvc 坐标），永不存表单结构/数据。办结前"先存表单再办结"的跨页桥（F5 已有）改为调外部表单服务的保存端点。

④ 单据适配器 —— serviceTask HTTP delegate + 生命周期 webhook

JavaDelegate（engine/delegate.rs:32）今天是进程内实现（如 RiskDelegate）。v2 加 HttpDelegate：节点配 URL，引擎把变量 POST 过去、拿返回写回变量——把"算风险/调外部逻辑"外包给第三方。加出站生命周期 webhook： 
// 出站（flow → 第三方业务系统），带签名头
POST {hook}  { event:"instance.started|completed|terminated", ... }
POST {hook}  { event:"task.created|completed|reassigned", taskId, assignee, ... }
// 入站（业务系统 → flow）：发起、办理、查询，全走 headless API §6
单据关联表（cmx_flow_biz_link）自持——只存 (biz_table, biz_id, instance_id) 三元指针，不存单据内容。真实单据数据由业务系统持有，需要时前端/webhook 去业务系统取。
四适配器的共性：全部是 Arc<dyn Trait> 注入 + 一个新 crate cmx-flow-adapters 装 HTTP 实现。引擎、store、handler 一律不感知外部是谁——配置切 URL 即换后端。默认 mock/自带实现让流程能脱离一切外部单独跑起来（开发/演示），生产配上真实外部服务 URL。

5. 前端一芯三壳 门户内嵌 · 可嵌组件 · headless

同一套 UI 逻辑（列表/卡片/过滤/分页/表单/审批轨迹/bpmn 画布 + 全 /api/flow/* 调用）抽成与宿主无关的核，三种壳包装：

壳① 门户内嵌 保留现状
继续以 native_pages 三页跑在 CMXPortalManager。ctx.host.renderRoot(shadow) + openWorkNode 门户链保留。零回归——今天能跑的照跑。这是"流程界面依赖门户"那一支。
壳② 可嵌 Web Component 新
把核封成框架无关 custom element：<flow-designer> / <flow-todo> / <flow-task-form>。第三方系统 <script> 引入 + 放标签 + 配 api-base/token 属性即用。可嵌进 React/Vue/Angular/原生任意框架。对标 cmx-mega-sheet（零运行时依赖单元素）。
壳③ 三方全自研 headless
只给 REST/gRPC API + SSE + OpenAPI（§6），第三方用自己的技术栈画设计器/待办/表单，一行流程前端代码都不用我们的。流程微服务对他们只是一组端点。
"抽核"怎么落地（关键改造）：今天三页面把 DOM 挂载写死在 ctx.host.renderRoot（门户 shadow）。抽核 = 把"取挂载根 + 取上下文(props)"参数化： 
// 核：mountFlowTodo(rootEl, { apiBase, token, tenant, user, onOpenTask })
//   门户壳：rootEl = ctx.host.renderRoot; onOpenTask = openWorkNode(门户链)
//   组件壳：rootEl = this.shadowRoot; onOpenTask = 派发 CustomEvent('flow-open-task')
//   —— 同一核，两种挂载/两种"打开任务"回调
openWorkNode 那 ~200 行门户特有逻辑塌缩成一个 onOpenTask 回调：门户壳里它是"开工作区 Tab"，组件壳里它是"派发事件让宿主决定怎么开"，headless 里根本不存在。
图标/主题复用：组件壳直接加载 cmx-ui5-runtime dist（预打包 ui5 web components + icon + SAP 主题），现有 <ui5-icon> 和 --sap* token 零改生效。三方若不想要 ui5，核也提供无 ui5 降级（demo 的纯 HTML 版已证明 UI 不依赖 ui5 也能看）。

6. Headless API 契约：三方自研设计器/待办 对外的正式接口

把今天的 /api/flow/*（内部端点）升级为对外正式契约：稳定版本化、OpenAPI 描述、认证 + 多租户、SSE 实时。分三组能力：

设计态（画流程） 
GET  /definitions
GET  /definitions/{k}
POST /definitions/draft
POST /definitions/{k}/publish
GET  /definitions/{k}/versions
POST .../versions/{v}/activate
三方自研设计器用 bpmn-js（或任意 BPMN 工具）产出 XML，POST draft/publish。BPMN 是标准，不锁我们的设计器。
运行态（发起/办理） 
POST /instances            起
GET  /instances/{id}       轨迹
POST /instances/{id}/cancel
POST /tasks/{id}/complete
POST /tasks/{id}/claim
POST /tasks/{id}/transfer
POST /tasks/{id}/delegate|addsign
业务系统入站发起、驱动流转。全部幂等/带业务键。
待办态（查任务） 
GET /tasks/my            我的待办
GET /todos/cc|initiated|done
GET /todos/filters
GET /forms/{key}         表单坐标
SSE /events?user=&tenant= 实时推
三方自研待办界面靠这组 + SSE 增量刷新（替今天的前端轮询）。
对外契约的四条硬要求（比内部端点多出来的）：
  1. 版本化前缀 /api/flow/v1/*，破坏性变更进 v2，老版本并存——三方集成不能被我们升级打断。
  2. OpenAPI/gRPC-proto 描述——三方能生成客户端 SDK。
  3. 认证 + 租户：每个请求带 JWT（用户级）或 API Key（服务间），中间件解出 tenant+user 强制过滤。
  4. SSE 事件流 task.created/completed、instance.*——三方 UI 实时更新，不必轮询。（cmx-job-core 的 SSE 中继可复用）
数据集类端点用 ZmcDataSet 出口（与 DOC/DCT/RPT 一致）：凡是对外返回业务行数据集（把某表/视图的 N 行整体交给消费方——如报表取数、待办/单据批量导出、给三方的行级数据流），走 cmx-database-pg 的 query_sql_zmc → encode_columnar_binary（列式 msgpack），驱动无关 · 零拷贝 · 可流式（峰值内存 O(单行)）。控制面小行读（单行→DTO、绑定/元数据查询）仍用 query_sql→DataSet 按名取值——不为统一而统一。判定线见 cmx-flowengine/README.md「数据读取约定」，范例见 cmx-doc 的 /api/doc/data.bin 家族。
身份在 headless 下怎么传？三方系统用自己的登录态换成对 flow 的 JWT（OIDC 或签发一个 flow 专用 token，claim 带 tenant/user/roles）。flow 不认第三方的 session，只认标准 token。这样"用户是外部的"贯穿到 API 边界：flow 从不管登录，只信任 token 里的身份声明，并用 §4① 的身份适配器把 role/org 引用解析成人。

7. 多租户 + 认证（在外部身份前提下） 谁是租户由外部定

多租户 flow 自持的表全部加 tenant_id（+ 复合索引），RuntimeStore trait 签名穿 tenant，每查带 WHERE tenant_id=$，RLS 兜底。tenant 从 JWT claim 来（外部 IdP 决定谁属于哪个租户）。大客户可选 db-per-tenant（cmx-database-pg 的 register_datasource(tenant, url) 天然支持）。
认证 OIDC/JWKS 验签中间件，只消费 claim（sub/tenant/roles），不自建用户体系。这与"身份外部化"是同一件事的两面：认证委托 IdP，人员/组织委托身份服务。接口级 RBAC 按 claim.roles 判（flow:design / flow:task）。
越权防线（多租户 + 外部身份的叠加风险）：①每条 SQL 强制 tenant 过滤（trait 签名逼着传，漏不了）；②RLS 数据库层兜底；③候选池/办理权校验只信服务端解析结果，不信前端传的 assignee；④headless API Key 绑租户，跨租户调用 403。

打包 / 运行
  • flow-server：单 Rust 二进制 → distroless 镜像；/healthz//readyz
  • flow-web（组件壳/静态站）：内嵌 ServeDir 或独立 CDN
  • docker-compose：flow-server + postgres +（可选）keycloak
  • 水平扩展：多副本共享 PG，定时器/webhook 用 SKIP LOCKED 认领防重

11. 工作量与风险矩阵 v2 诚实评估

方面量级难度说明
引擎核（model/bpmn/engine）0—原样，零改
持久化 + 多租户中中加 tenant 列/签名 + RLS（绿地但有成熟范式）
flow-http 重写（脱 cmx-api）中中低装配换、handler 搬，机械活
四外部适配器中中trait 已在（3 个），新增 HTTP 实现；表单加两 kind；delegate 加 HTTP 型
认证小中中接标准 OIDC 库，只消费 claim
Headless API 正式化小中低中端点已全在，加版本/OpenAPI/SSE/APIKey
前端抽核 + 门户壳中中参数化挂载 + onOpenTask 回调；门户不回归
可嵌 Web Component 壳中中封装 + 主题 + 降级；有 cmx-mega-sheet 范本
结构性优势（v2 更顺）
  • "外部化"正是三个注入 trait 的设计初衷——trait 注释明写"引擎不依赖 IAM/DB"
  • 表单绑定已有 kind 分派，加 external 型是延长线不是新机制
  • 平台 center_client 早为外部 flow 服务预留——集成契约已存在
  • headless 端点今天全在，正式化是包装非新建
  • 前端核与门户壳可切分，切完门户仍能用同一核
需留心
  • 外部服务可用性：身份/表单服务挂了流程要能优雅降级（缓存 id、显示 id、表单 iframe 兜底）
  • N+1 解析：候选人/展示名批量端点 + 缓存，别每任务一次往返
  • 多租户越权：RLS + trait 强制传 tenant 双保险
  • 契约稳定性：headless 对外后破坏性变更要走版本，不能随意改
  • 抽核回归：门户壳改造需 CDP 全量回归今天已验的办理/查看/叠加
v2 总评：方向与代码的天然结构高度吻合——三个注入 trait 本就是为"外部实现"设计的，表单 kind 分派本就可扩展，平台本就为外部 flow-center 留了位。所以"身份/组织/表单外部化"不是硬改，是兑现既有扩展点。真正的新增是：flow-http 脱壳（一次性）、多租户（绿地）、可嵌组件 + headless 正式化（增量）。引擎一行不改，前端一芯三壳并存，一份二进制三种部署姿态。
