Design Proposal · M4.1·M4.2·M4.3 全部已落地实测

cmx-flow M4 设计方案 · 抄送 / 转签 + 角色 · 岗位

在 M1~M3 + M2.5 已落地的流程语义之上，补齐「人与组织」维度：办理人不再是裸字符串，而是接入 IAM 的角色/岗位；并加入抄送（知会+已读）与转签家族（转办 / 加签 / 委派）。

M4.1 候选人：✅ 已落地 M4.2 抄送：✅ 已落地 M4.3 转签：✅ 已落地 身份：复用 cmx-iam 不改：M1~M3 语义

要解决什么

前四个里程碑把 BPMN 的流程语义做透了（顺序、分支、并行、会签/或签、定时器、取消）。但办理人始终是 BPMN 里写死的字符串 （flowable:assignee="经理"）——引擎不认识「谁是经理」「财务部有哪些人」。M4 补上正交的组织身份维度， 并加入两类审批协作动作。四个诉求可归为两层：

🧑‍💼

角色 / 岗位设置 地基

候选人来源从「静态字符串」升级为「角色 / 岗位 / 部门」表达式，运行期解析成真实用户集合。角色复用现有 IAM，岗位与组织补齐。

📋

抄送 CC 知会+已读

把流程进展知会给相关人，不阻塞、不产生待办，带已读/未读追踪。区别于「审批」的只读旁路。

🔁

转签（转办家族）3 动作

办理人把任务转出：转办（彻底换人）、加签（前/后插临时审批人）、委派（代办，所有权仍归己）。

🏢

组织 / 部门 补齐

现有 cmx_user.org_id 是悬空引用——没有组织表。补一棵部门树，让岗位/数据权限有所依附。

一、家底盘点：已有什么，缺什么

动手前先看清库存。项目已有完整的 IAM 体系，M4 的第一原则是复用，不重造。

✅ 已有（直接复用）

资产形态M4 怎么用
cmx_user用户表，含 org_id办理人 / 抄送人 / 转签目标的唯一身份来源
cmx_role角色表（code/name/role_group_id）候选人表达式 role(code) 的解析目标
cmx_role_group角色组（树形）角色分类，管理台展示用
cmx_user_role用户—角色关联由角色反查用户集合（会签展开的来源之一）
cmx_role_permission角色—权限关联管理台的功能权限控制（谁能配流程）
cmx-iam crateuser / role / permission 服务flow 侧通过其查询接口取用户/角色，不直接读表

❌ 缺（M4 补齐）

缺口现状补法
组织 / 部门树cmx_user.org_id 有值但无对应表，悬空引用新建 cmx_org（部门树），让 org_id 落地
岗位 Position完全没有「岗位」概念（如"财务主管""分行行长"）新建 cmx_position + cmx_user_position
候选人解析flow 的 assignee/candidate_groups 只是字符串，不接 IAM引擎侧加 AssigneeResolver，把表达式解析成用户集

转签痕迹无（任务只有 assignee 一个字段）新建 cmx_flow_task_delegation（转办/加签/委派台账）
复用原则：M4 绝不新建流程专用的用户表 / 角色表。角色 100% 用 cmx_role；用户 100% 用 cmx_user。 flow 只新增「组织 / 岗位」这两块 IAM 尚缺的通用能力（放在通用前缀，供全局复用），以及「抄送 / 转签」这两块流程专属的运行态表（cmx_flow_ 前缀）。

二、身份维度：候选人表达式如何解析

核心抽象：BPMN 里的办理人配置不再是「一个人名」，而是一个候选人表达式，引擎在令牌到达 userTask 时把它解析成真实用户集合。

BPMN 定义（设计态，静态） 解析器（运行态，接 IAM） 产出（真实用户） ───────────────────────────── ───────────────────────── ────────────── flowable:assignee = "user(u_1001)" ──┐ flowable:candidateUsers = "u_1001,u_1002" ─┤ AssigneeResolver flowable:candidateGroups= "role(finance)" ─┼──► ├─ user(id) → 该用户 ──► [u_1001] 自定义 cmx:position = "pos(cfo)" ─┤ ├─ role(code) → cmx_user_role 反查 ──► [u_1001,u_1077] 自定义 cmx:org = "org(d_fin)" ─┘ ├─ position(code)→ cmx_user_position ──► [u_1077] └─ org(id) → cmx_org 下的人 ──► [u_1001,u_1077,…] （解析结果落 candidate，见下）
user() 指定人 role() 按角色（复用 cmx_role） position() 按岗位（新建） org() 按部门（新建）

解析产出两种落法：①单人 → 直接置 task.assignee（M1 老路，零改动）； ②多人候选 → 落 cmx_flow_task_candidate（任务候选池），谁认领谁办（对齐 Flowable 的 claim 语义）。 候选池也天然是会签（M3）的展开来源——role(finance) 展开成 N 个会签子任务。

解析时机与快照：候选人在令牌到达时解析一次并落库（快照式），不在每次查询时实时算。理由：① 与引擎「等待态即提交点」的聚合快照一致； ② 避免"审批中途某人被调离角色"导致待办凭空消失——已生成的待办按当时快照走，可审计、可复现。

三、抄送 CC：知会 + 已读

抄送 = 在某节点把「进展」只读地知会给一组人。不阻塞流程、不产生待办、不影响令牌推进——它是流程的旁路投影，与审批任务正交。

触发方式（两种，可并存）

  • 节点配置抄送：BPMN 的 userTask 上配 cmx:cc="role(dept_head), user(u_boss)"，令牌离开该节点时自动抄送。
  • 办理时手动抄送：办理人在完成任务时附带一个抄送名单（前端「抄送给」多选），即时生成。

时序

令牌到达/离开 userTask │ ├─► 正常审批流（产生 task，等待办理） ← 主干，不受抄送影响 │ └─► 生成抄送记录 cmx_flow_cc（每个被抄送人一条，unread） │ ▼ 被抄送人「我的抄送」列表可见 → 点开 → 标记 read（记 read_at） │ ▼ 流程完成/取消，抄送记录随实例归档，不阻塞任何环节
与待办的区别：抄送记录不进 cmx_flow_task（那是「要办的」），单独进 cmx_flow_cc（「知会的」）。 前端「我的待办」与「抄送我的」是两个入口。已读状态是抄送独有的，任务没有「已读」只有「办结」。

四、转签家族：转办 / 加签 / 委派

三个动作都作用在一个已存在的待办任务上，区别在于「所有权是否转移」与「是否新增审批环节」。统一记入 cmx_flow_task_delegation 台账，可追溯完整流转链。

① 转办（改派）换人

[任务 T · assignee=张三] ──转办给→ 李四 │ ▼ [任务 T · assignee=李四] 同一个任务，办理人从张三改成李四；张三退出，李四接手 台账：{task, from:张三, to:李四, type:TRANSFER, reason}

② 加签（向前 / 向后）加环节

向前加签（先让王五审，再回我办）： [任务 T · 张三] ──向前加签→ 王五 │ ▼ [临时任务 · 王五] ──王五办结→ [任务 T · 张三 恢复待办] 王五审完，控制权回张三 向后加签（我先办，再交王五审）： [任务 T · 张三] ──向后加签→ 王五，张三办结 │ ▼ [临时任务 · 王五] ──王五办结→ 继续原流程 张三办完不直接走，先经王五

加签会动态插入一个临时审批环节——这是三者中最重的，需引擎支持「运行期动态子任务」，且加签可嵌套（王五还能再加签赵六）。

③ 委派（代办）代办不换主

[任务 T · owner=张三, assignee=张三] ──委派给→ 李四 │ ▼ [任务 T · owner=张三, assignee=李四] 李四代办，但 owner 仍是张三 │ ▼ 李四办结 → 回到 owner 张三「确认」（可选）→ 才真正完成 台账：{task, owner:张三, delegate:李四, type:DELEGATE}
转办 vs 委派的分野：转办后张三与该任务再无关系；委派后张三仍是 owner，李四只是 assignee（代理人）。 是否需要「委派办结后回 owner 确认」是一个可配开关，建议 M4 先做不回confirm 的简单委派，回确认留后续。

对任务表的影响

cmx_flow_task 需从「单 assignee」升级为区分 owner（所有者）/ assignee（当前办理人）；加签需要 parent_task_id（临时任务挂在原任务下）。这几列是加列（ALTER），不动既有语义——单实例任务 owner=assignee，行为与 M1 一致。

七、建议里程碑拆分

M4 面较宽，建议拆成三个可独立验收的子步，每步都可端到端跑通 + 落 fico 库 + 更新文档三件套。

子步范围产出
M4.1 身份地基：cmx_org + cmx_position + cmx_user_position；AssigneeResolver 契约 + IAM 适配器；候选人表达式解析 + claim 认领 候选人从字符串升级为 role/position/org 解析；「我的待办」按真实用户查
M4.2 抄送：cmx_flow_cc；节点配置抄送 + 手动抄送；已读追踪；「抄送我的」列表 知会+已读闭环，最独立、风险最低，可先落
M4.3 转签：task 加列 + cmx_flow_task_delegation；转办 → 委派 → 加签（按此难度序） 转办家族三动作；加签的动态临时任务是最难点，压轴

管理台（角色/岗位/组织的增删改查界面）建议与 M4.1 并行，或复用现有 IAM 管理台扩展岗位/组织页签。

八、风险 · 边界 · 非目标

关键风险

  • 候选人快照 vs 实时：已决定快照式（到达时解析落库）。需接受"审批中角色变更不影响已生成待办"，并在文档写明。
  • 加签的动态节点：加签在运行期插入原定义里没有的临时任务，可嵌套。需引擎支持"非定义驱动"的令牌/任务，是本里程碑最大技术点，务必配充分测试。
  • 会签 × 候选人：role(finance) 用于会签节点时，M3 的 collection 展开需与候选人解析对齐（把解析出的用户集作为 collection）。两者交界要理清。
  • org_id 历史数据：现有 cmx_user.org_id 可能已有值但无对应 cmx_org 记录。建表后需数据校验/回填，避免解析空指。

本次非目标（M4 不做，留后续）

  • 委派办结后回 owner 二次确认——先做直通委派。
  • 抄送的站内信 / 邮件 / IM 推送——只落库 + 前端列表，不接通知渠道。
  • 基于岗位 level 的自动逐级升级（如"审批人的上级")——岗位职级字段预留，逻辑后续。
  • 数据权限（cmx_role.data_scope 那套「本部门/本人」）——本次只做候选人解析，不做数据行级权限。
不动既有：M1~M3 + M2.5 的流程语义、表结构、测试全部不改。M4 全靠加列（幂等）+ 新表 + 新扩展点接入，既有 39 个测试须继续全绿作为回归基线。
本文档为 设计方案，非已实现结构。评审通过后按 M4.1 → M4.2 → M4.3 落地，每步补迁移 + 更新 schema 文档。
