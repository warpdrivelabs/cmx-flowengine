## 1. 测试模型

### 1.1 主流程 `travel_expense`（差旅报销申请，7 语义节点）

```
[提交报销单]
      │
      ▼
(部门经理审批  u_mgr)            ← 业务经理审批节点
      │
      ▼
  ◇ 金额判断 ◇  default=小额
   ├──大额 ${amount>20000}──▶ (总监审批  u_director) ──┐
   └──小额（默认）───────────────────────────────────┤
                                                       ▼
        [财务复核·按组织路由]  callActivity  cmx:calledKey="fin_review"   ← 不同组织走不同子流程
                                                       │
                                                       ▼
                                          (出纳打款  u_cashier)
                                                       │
                                                       ▼
                                               [报销完成]
```

- 分支：排他网关 `gw_amount`，`大额(>20000)` 与 `小额(默认)` 两条出边，汇聚于 `fin_review`。
- 组织路由：`fin_review` 是 **callActivity**，`cmx:calledKey="fin_review"` 为逻辑名，真实调用哪个子流程由「组织绑定表 + 实例发起组织」运行时解析。

### 1.2 财务复核子流程（两套，同一逻辑名 `fin_review` 差异化）

| 子流程定义 | 用途 | 节点链 |
|-----------|------|--------|
| `fin_review_hq`（总部财务三级复核，5 节点） | 总部/大公司严格三级会审 | [开始]→(财务初审 u_fin1)→(财务经理复核 u_fin2)→(财务总监审批 u_fin3)→[通过] |
| `fin_review_branch`（分公司财务单签，3 节点） | 分公司轻量单签 | [开始]→(分公司财务经理单签 u_finb)→[通过] |

### 1.3 组织机构树（seed 于身份库 `cmx.cmx_org`，带物化 path）

```
总部 zongbu  (/zongbu)
 ├─ 北京财务部 fin_bj  (/zongbu/fin_bj)
 └─ 上海财务部 fin_sh  (/zongbu/fin_sh)
```

### 1.4 组织子流程绑定（`cmx_flow_subflow_binding`，设计工作台「组织路由」面板可见）

| calledKey | 组织 | → 目标子流程 | 语义 |
|-----------|------|-------------|------|
| fin_review | 总部 zongbu | fin_review_hq | 精确绑定 |
| fin_review | 上海财务部 fin_sh | fin_review_branch | 精确绑定 |
| fin_review | （默认兜底 orgId=null） | fin_review_hq | 兜底 |

> 部署产物：`docs/biz-test/{travel_expense,fin_review_hq,fin_review_branch}.bpmn`（纯语义 BPMN，无 DI；设计器打开时自动 BFS 布局，源码 `web/core/design-workbench.js:1910-1919`）。

## 2. 场景 A — 总部·大额 happy path（全链路办结）

**输入**：`orgId=zongbu`，`amount=50000`（大额），`initiator=u_emp`，`businessKey=CLYX-2026-001`。

| ④ | u_fin1→u_fin2→u_fin3 逐级办结 | `complete ×3` | 子流程三级顺序推进；末级办结后**子实例 COMPLETED**，父实例被唤醒回主流程，令牌到 `cashier` |

## 5. 场景 C — 退回 / 驳回（reject）

**载体**：`businessKey=CLYX-2026-005`（总部·¥30000 大额），实例 `53aec125…`。

### 5.1 reject-targets 目标枚举（只读契约）

选中「总监审批 director」查询可退回目标：

```json
{ "currentNode":"director", "rejectable":true, "defaultTarget":"mgr",
  "targets":[ {"bpmnId":"mgr","name":"部门经理审批","isDirectPredecessor":true,"distance":2} ] }
```

✅ 反向 BFS 正确识别上游用户任务 `mgr`，标注直接前驱与跳数（director→网关→mgr=2 跳）。

### 5.2 主流程·默认前驱退回

总监节点 `reject`（`targetBpmnId` 留空 → 回直接前驱）：
- ✅ 令牌从 `director` 回落 `mgr`，`u_mgr` 重新待办「部门经理审批」（`active:["mgr"]`）。

### 5.3 子流程·指定节点跨级退回

重走至子流程 `fin_review_hq`，办结 fin1、fin2，在「财务总监 fin3」查询目标：

```json
{ "currentNode":"fin3", "defaultTarget":"fin2",
  "targets":[ {"bpmnId":"fin2","isDirectPredecessor":true,"distance":1},
              {"bpmnId":"fin1","isDirectPredecessor":false,"distance":2} ] }
```

fin3 指定 `targetBpmnId=fin1` 退回（**跨级、跳过 fin2**）：
- ✅ 令牌从 `fin3` 直接回落 `fin1`（`active:["fin1"]`），跳过中间的 fin2 → **指定节点退回成立**。
- 实例保留在 `fin1` 返工态，待办可查。

**关键断言**：reject-targets 契约（rejectable / defaultTarget / isDirectPredecessor / distance）完整；默认前驱退回（主流程）+ 指定节点跨级退回（子流程内）双路径均正确。

## 6. 场景 D — 取回 / 撤回（withdraw）

### 6.1 未处理时发起人取回（D-a）

`businessKey=CLYX-2026-006`，实例 `8f403176…`，`initiator=u_emp6`，令牌在 `mgr`（未办）。

| 检查 | 端点 | 实测 |
|------|------|------|
| 发起人可否取回 | `GET /instances/{id}/withdrawable?user=u_emp6` | `{"withdrawable":true}` ✅ |
| 非发起人可否取回 | `?user=u_other` | `{"withdrawable":false,"reason":"仅发起人可取回本流程"}` ✅ |
| 执行取回 | `POST /instances/{id}/withdraw {user:u_emp6}` | `code:0` 成功 |

取回后：令牌回 `mgr`，任务**改派回发起人 u_emp6**（`open:[{node:mgr, who:u_emp6}]`）——发起人可修改后重新提交。

**WITHDRAW 台账**（`instance_view.delegations`，可审计）：
```json
{"kind":"WITHDRAW","fromUserId":"u_emp6","toUserId":"u_emp6","reason":"信息填错，取回修改","createdAt":"2026-08-16T03:11:38…"}
```

### 6.2 下游已办结后 strict 拒绝取回（D-b）

`businessKey=CLYX-2026-007`，实例 `991ca740…`，`initiator=u_emp7`。部门经理办结后：
- ✅ `withdrawable?user=u_emp7 → {"withdrawable":false,"reason":"下游已有环节办结，不可取回（strict 策略）"}`
- ✅ 强行取回被拒：`{"code":1,"msg":"任务不可办理: 下游已有环节办结，不可取回（strict 策略）"}`

**关键断言**：取回准入三态（发起人可取 / 非发起人拒 / 办结后 strict 拒）全部正确；改派语义（回发起人处返工）+ 台账留痕齐备。

> 策略说明：默认 `strict`（下游全未办结才可取回）；定义可声明 `cmx:withdrawPolicy="lenient"`（仅当前未办结即可），本次用默认 strict。
