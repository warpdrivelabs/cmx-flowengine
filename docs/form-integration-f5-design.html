1 · 范围边界 F5 做什么、不做什么

✓ F5 做

  • task-form content 区接 CmxMasterSlave.loadDoc 拉真单据
  • 元数据驱动渲染字段/主从表格（复用 doc 的 meta）
  • formMode=readonly/approve 只读审阅、edit 可改
  • formFields 白名单：只允许改指定字段

✕ F5 不做（够用即止）

  • 字段级权限（超 formFields 的细粒度）——留后续
  • 单据自身的业务校验规则引擎——复用 doc 既有校验
  • 引擎 / 编译器 / F1-F4 已定的后端——不碰

3 · 架构决策：内联 vs 委托 F5 最关键的选择

task-form 的 content 要渲染真单据，有两条路。这个选择决定代码量、隔离性、与 F3 html 路径的一致性。

方案 A：内联渲染 不选

把 doc-loader 的 loadMeta/渲染/collector 代码 fork 进 task-form.js，content 自己建 CmxMasterSlave + grid。

  • ✕ 复制几百行 doc 渲染逻辑，双份维护
  • ✕ 与 doc-loader 演进漂移
  • ✓ 单页自包含

方案 B：委托 doc-loader 作 content 视图 F5 选这个

content 视图直接指向现有 portal.doc.doc-loader（native_pages），props 传单据坐标 + filter；审批控制台仍在 property（task-form）。

  • ✓ 零复制——doc-loader 原样复用，它已实证
  • ✓ 与 F3 的 html-pages 路径同构（content 换页，property 办理）
  • ✓ doc-loader 升级自动惠及流程
  • △ 需给 doc-loader 补一个「单记录 + formMode/formFields」参数入口
决策：方案 B（委托），与 F3 html 路径完全同构。回顾 F3 的统一架构——审批控制台永远在 property（task-form），content 区按表单类型换不同页：native 简单展示走 task-form content、html 表单走 html_pages、真单据走 doc-loader。三类表单一个骨架。F5 只需：① 待办中心的 FORM_MAP.kind 增加 'doc' 类型，content 视图指 portal.doc.doc-loader 并传坐标 + filter:'主键:bizId'；② 给 doc-loader 补 formMode（只读/可编辑）与 formFields（白名单）两个 props 的消费（薄改）。审批、办结、意见留痕全部不动（property 侧 F3 已成）。

6 · 可写收紧：formMode + formFields F5 给 doc-loader 补的薄改

这是 F5 对 doc-loader 唯一实质性的功能补充：让它按流程任务的上下文，控制"能不能改、能改哪些字段"。

6.1 formMode → 整体读写

formModedoc-loader 行为
readonly / approve所有 grid editable=false、表单只读（审阅态，绝大多数审批环节）
edit允许编辑，但受 formFields 白名单收紧（§6.2）

doc-loader 的 grid 已有 editable 选项（InteractionController 的 editable 开关）；表单区列的 editMode 同理。F5 加一个「按 formMode 统一压只读」的开关。

6.2 formFields → 字段级白名单

// doc-loader 建列模型时，若有 formFields 白名单：不在名单内的列强制 editMode='readonly'
function applyFieldWhitelist(colModel, formFields) {
  if (!formFields || !formFields.length) return   // 空 = 不限制(edit 下全可改)
  const allow = new Set(formFields)
  colModel.members.forEach((col) => {
    if (!allow.has(col.id)) col.editMode = 'readonly'   // 白名单外只读
  })
}

formFields 来自 userTask 的 cmx:formFields（F2 已解析进 IR、经 /tasks/my 带到待办）。例：某环节只允许改「摘要」和「审批金额」，其余分录只读——白名单 summary,approve_amount。

为什么放 doc-loader 而非 task-form：字段可写性是渲染层的事，必须在建列模型时施加。task-form 的 property 审批控制台够不着 content 里的 grid 列。所以 formMode/formFields 作为 props 传给 doc-loader，由它在建模时消费。这也保持了「content 自管渲染、property 自管审批」的干净分层。

7 · 存回：改动收集 + 保存 edit 环节真写 cf_*

可编辑环节办结前，若单据被改了，要真存回业务表。复用 doc-loader 的 ChangeSetCollector（doc-loader:336/360 实证）。

7.1 存回时机：办结前自动存

1
办理人在可编辑单据上改了字段（doc-loader 的 ChangeSetCollector 自动追踪脏数据）。
2
点 property 区「同意」办结。task-form 的 complete 先通知 content 的 doc-loader 存单据，再调 flow complete。
3
跨页存单据的桥：complete 前广播一个 cmx-flow-before-complete 事件；doc-loader 监听 → 若脏则 collector.export() → saveDocData(...) → 回执。task-form 等存完再 flow complete。
// doc-loader 侧：监听办结前事件，脏则先存单据（409冲突/422校验要处理）
window.addEventListener('cmx-flow-before-complete', async (e) => {
  if (!state.collector || !state.collector.isDirty()) return ack(e, {saved:false})
  const changes = state.collector.export()
  try {
    const r = await saveDocData(null, def, {saveMode:'merge', changes})
    state.collector.refreshBaselines(r.updatedAt); state.collector.reset()
    ack(e, {saved:true})
  } catch (err) {
    if (err.conflict) ack(e, {saved:false, error:'单据已被他人修改，请刷新'})  // 409
    else if (err.violations) ack(e, {saved:false, error:formatViolations(err.violations)})  // 422
    else ack(e, {saved:false, error:err.message})
  }
})
时序细节：「先存单据再办结」的顺序保证——单据存失败则中止办结（否则流程走了但数据没存，不一致）。用一个带 Promise 的事件（或直接调 doc-loader 暴露的 getPageApi().saveIfDirty()）等存回结果。这是 F5 唯一的跨页协调点，其余全是各自现成能力。备选：doc-loader 暴露 saveIfDirty() 到 host.workspace.pageview，task-form 直接调（比事件更可靠）。
