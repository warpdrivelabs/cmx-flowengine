定位与设计哲学

一句话：Flowable 的语义 + Rust 原生的架构。不照抄 Java 引擎的 OOP 继承树，而用 Rust 的表达力重写内核。

  • arena + 索引，非指针图：所有节点存 Vec<FlowNode>，节点间用 NodeId（下标 newtype）引用，杜绝 Rc<RefCell> 共享可变图。
  • enum dispatch，非行为类层级：BPMN 元素类型是 NodeKind 枚举，编译期穷尽匹配，加一种节点编译器逼你补全所有分支。
  • 「等待态即提交点」：每个 BPMN 等待态（userTask / callActivity）恰好对应一次数据库事务提交。聚合快照（实例 + 令牌 + 任务 + …）原子读写，无中间态泄漏。
  • 受控手写解析器，零重依赖：条件表达式、ISO8601 时长、候选人表达式全部手写，不引 rhai / chrono-duration 等第三方，行为可控。
  • 可注入扩展点，引擎中立可测：委托执行、时钟、候选人解析、子流程路由都是 trait，宿主注入实现。引擎不依赖任何 DB / IAM，内存态测试全程无外部依赖。

一、里程碑演进

M1顺序审批 · 内核奠基
令牌执行内核、arena/enum/聚合快照、受控 DSL 表达式求值、serviceTask 委托（JavaDelegate 扩展点）、exclusiveGateway 条件分支。引擎的心脏。
M2并行网关 · 历史归档
parallelGateway fork/join（AND 语义、JOINING 态令牌合流）；RU/HI 分离，实例终态同事务归档到历史表（含存续/办理时长）。
M2.5边界定时器 · 可注入时钟
中断/非中断型边界定时器（限时未办自动升级/催办）；Clock 扩展点——测试用 TestClock 拨快，定时器确定性可测；手写 ISO8601、find_due_jobs 跨实例扫描。
M3多实例会签/或签 · 实例取消
并行会签（N 人齐办）+ 顺序或签（逐个）；completionCondition 提前收口（过半通过/驳回终止）；实例取消激活 TERMINATED 归档。
M4.1角色 / 岗位候选人
办理人从裸字符串升级为 role()/position()/org()/user() 表达式；AssigneeResolver 扩展点接现有 IAM；多人候选落池、claim 认领。补建组织/岗位表。
M4.2抄送 CC
只读旁路知会——不阻塞流程、不产生待办、带已读追踪；节点配置抄送 + 手动抄送；「抄送我的」跨实例查询。
M4.3转签家族
转办（彻底换人）/ 委派（代办不换主）/ 加签（动态临时任务，可嵌套）；完整流转链台账可追溯。
M5.1子流程 callActivity · 同步等待
主流程调用独立部署的子流程并同步等待；WAITING_SUBFLOW 令牌、父子实例、complete_subflow 逐层唤醒、变量映射；子流程复用完整内核、可嵌套。
M5.2子流程按组织路由
同一主流程，不同组织跑不同子流程。callActivity 写逻辑 key，SubflowRouter 扩展点按实例组织解析：精确绑定 → 沿组织树 path 向上继承 → 默认兜底。

四、贯穿设计：四个可注入扩展点

这是整个引擎最一致的设计线索——凡是「引擎需要外部世界的东西」，都定义成 trait，宿主注入实现。生产接真实基础设施，测试用假实现，引擎本体永远中立可测。

JavaDelegateM1

serviceTask 的执行体。Java 靠类加载 + EL 反射；这里用显式注册表，无反射、类型安全。

ClockM2.5

「现在几点」。生产 SystemClock，测试 TestClock 手动拨快——定时器逻辑确定性可复现，无需真实等待。

AssigneeResolverM4.1

候选人表达式 → 真实用户集。生产接 cmx-iam（角色/岗位/部门反查），测试用固定映射。

SubflowRouterM5.2

逻辑子流程 key + 组织 → 具体子流程。生产查绑定表 + 组织树继承，测试用假路由。

为什么这条线索重要：它让「44 个内存测试完全无外部依赖、毫秒级跑完」成为可能，也让引擎能被 wasm / 嵌入式 / 不同 IAM 体系复用——引擎只认 trait，不认具体实现。

六、令牌状态机（引擎心脏）

令牌是流经流程图的执行指针。它的状态迁移就是引擎的推进逻辑——每一种「挂起等待」都对应一次事务提交点。

┌──────────────────────────────────────────────┐ ▼ │ startEvent ──► Active ──推进──► ┬─ userTask ────► Waiting ──办结──┘ （等人办） （可推进） ├─ 并行 join ──► Joining ─兄弟到齐┘ （等兄弟令牌） ├─ callActivity ► WaitingSubflow ─子完成┘ （等子实例·M5） └─ endEvent ───► Ended （消费令牌） 所有令牌 Ended → 实例 Completed；实例取消 → 全令牌 Ended + Terminated
三种「挂起等待」的统一与区别：Waiting 等人工办结、Joining 等兄弟令牌到齐（结构性阻塞，同段内消解）、WaitingSubflow 等子实例完成。它们并列却各有唤醒信号，天然支持「并行网关下并发调多个子流程」这类组合。

八、关键设计决策 & 踩过的坑

决策

  • 快照式候选人解析（M4.1）：令牌到达时解析一次落库，不实时算——避免「审批中角色变更导致待办凭空消失」，可审计可复现。
  • 可注入时钟先重构再加功能（M2.5）：把散落的 now() 改为参数传值，先跑全回归证明无损，再叠定时器——隔离重构风险与新功能风险。
  • 加签共享父令牌（M4.3）：临时任务与原任务共用令牌（令牌不动），父任务挂起 SUSPENDED，临时办结后恢复——不产生游离令牌，可嵌套。
  • 子流程复用完整内核（M5.1）：子流程就是「被父令牌等待着的普通实例」，不为它另写执行逻辑——所以子流程能用会签/定时器/转签全部能力。

踩过的坑（已记入项目记忆）

  • 子完成经 complete_task 须回调唤醒父（M5.1）：子流程走 complete_task 完成时，必须判「已完成 + 有父」再调 complete_subflow，否则子完成但父永久挂起。
  • completionCondition 要读实例变量（M3）：过半/驳回条件求值需实例变量做底，用下标定位 scope + 不相交字段借用。
  • tokio-postgres 严格类型：可空 TIMESTAMPTZ/BIGINT/JSONB 绑 NULL 必须带类型标记（NullTyped），裸 Null 会 WrongType。
  • 迁移编号冲突（M5.1/M4.3 都占 003）：M5.1 重编号 004 避冲突。
