## 001 · 出站 webhook 多业务系统接入限制

> 记录日期：2026-08-17 ｜ 来源：M7 主数据 CR 审批对接（`mdm_cr_approval`）上线后的评审追问。

### 一、现状（代码事实）

出站生命周期 webhook 的实现位于 `crates/cmx-flow-adapters/src/webhook.rs`，配置读取位于
`crates/cmx-flow-adapters/src/config.rs`（`WebhookConfig::from_env`）。当前能力：

| 能力 | 现状 | 代码位置 |
| --- | --- | --- |
| 多回调端点 | ✅ 支持。`FLOW_WEBHOOK_URLS` 为逗号分隔列表，每条事件 POST 给**全部** URL | `webhook.rs` `spawn_worker`（`for url in &urls`） |
| 配置来源 | ⚠️ 仅环境变量（`.env` / 进程 env），toml 未承载 | `config.rs` `WebhookConfig::from_env`（纯 `std::env`） |
| 事件路由 | ❌ 无。广播模型，不带订阅过滤 | 同上 |
| 签名密钥 | ⚠️ 全局唯一一把 `FLOW_WEBHOOK_SIGNING_KEY`，所有端点共用 | 同上 |
| 投递方式 | ⚠️ 单后台 worker 串行消费，逐 URL 顺序 await，失败指数退避（1s/2s/4s…上限 64s，默认重试 3 次） | `webhook.rs` `deliver` |
| 持久化 | ❌ 内存 mpsc 队列（容量 1024），进程重启丢事件；队列满静默丢弃（webhook 定位为通知，非关键路径） | `webhook.rs` `WebhookSender` |

### 二、多业务系统场景的三个短板

流程引擎一旦对接**多个业务系统**（如 MDM 之外的财务、OA），当前模型的实际问题：

1. **无事件路由（广播 + 接收方自行过滤）**
   每个端点收到**所有**系统的事件。MDM 侧在回调入口做了五规则过滤
   （biz 归属过滤 / definitionKey 过滤 / 当前实例校验 / terminated 幽灵事件拦截 / try_set 抢占写，
   见 cmx-container `cmx-mdm-api/src/handlers/flow_cb.rs`），所以安全；但：
   - 每个新接入方都得重做一遍过滤逻辑，容易漏；
   - 存在**信息泄露面**——A 系统的回调端点会收到 B 系统的 businessKey 与单据变量投影。

2. **签名密钥全局唯一**
   所有端点共用一把 HMAC 密钥。跨团队 / 跨安全域接入时不成立——持有密钥者可向任一端点伪造事件。

3. **串行投递互相拖累**
   单 worker 串行 `for url` await，一个慢 / 挂的端点（含最长 64s 的退避重试）会拖住**所有**端点的
   事件投递。不阻塞业务（后台队列），只延迟通知，但多系统下放大。

另有一条独立债务：**内存队列重启丢事件**。MDM 侧已有懒同步自愈兜底（回调失败 5 分钟窗口内
查询单据时回查引擎状态），故不紧急；其他接入方无此兜底前需知悉。

### 三、演进方案（已论证，待排期）

**方案 A · 配置层多 target（推荐首版）**

toml 改为数组，每个 target 独立密钥 + 可选 definitionKey 订阅过滤 + 每个 target 独立 worker
（互不拖累）；不配 targets 时回退现有单配置，兼容现状：

```toml
[[webhook.targets]]
urls = "http://127.0.0.1:8080/api/mdm/flow/callback"
signing_key = "mdm_flow_hook_dev_secret"
definition_keys = "mdm_cr_approval"   # 空 = 订阅全部

[[webhook.targets]]
urls = "http://oa-system/flow/callback"
signing_key = "oa_own_secret"
```

同时补 toml 承载：flow-server 的 `apply_toml_env()`（`crates/cmx-flow-server/src/main.rs`）
已有「toml 段 → `set_var` 注入 FLOW_*（env 未设时）」通道，`[auth]`/`[datasource]` 均走此路；
加 `[webhook]` / `[[webhook.targets]]` 段即可，adapters crate 可保持零平台依赖。
改动集中三处：`config.rs`（解析）+ `webhook.rs`（按 target 起 worker + definitionKey 过滤）+ `main.rs`（toml 注入段）。规模小。

**方案 B · 注册订阅模型（完整形态，暂无诉求）**

提供 `POST /api/flow/webhooks` 注册接口（URL + 密钥 + 订阅定义列表），落 pg 表，配管理页面。
适用于多租户 / 动态接入。当前没有此诉求，不做。

### 四、相关决策记录

- **2026-08-17**：上述限制记录在案；**MDM 侧暂不做修改**（其五规则过滤 + 懒同步兜底已防御
  广播噪音与丢事件风险），演进按方案 A 在 flowengine 侧实施，待排期。

## 002 · 表单注册表 `cmx_flow_form_binding` 无维护页面

> 记录日期：2026-08-18 ｜ 来源：排查「`api/flow/forms` 相关接口有没有前端入口」时的代码走读结论。

### 一、现状（代码事实）

后端接口齐全（`crates/cmx-flow-app`），表 DDL 位于 `src/biz_link.rs:60`（`CREATE TABLE cmx_flow_form_binding`，
`form_key` 主键）：

| 接口 | 能力 | 代码位置 |
| --- | --- | --- |
| `GET /api/flow/forms` | 列表（按 form_key 排序） | `lib.rs:140`（`list_form_bindings`） |
| `POST /api/flow/forms` | upsert（form_key 冲突整行更新） | `lib.rs:140`（`save_form_binding`） |
| `GET /api/flow/forms/{key}` | 单条查询 | `lib.rs:142` |

绑定字段：`kind`（workspace / html / native）、`workspace_node`、`native_page`、`native_view`、`html_page`、
`biz_table`、`domain/application/module`（DAM 归属）、`file`、`pk_field`、`title`、`console`（platform / none）。
引擎启动时 `seed_form_bindings()`（`biz_link.rs:727`）幂等种入 3 条示例（`pay.review`、`pay.review.html`
为 html，`expense.form` 为 workspace）。

前端（`web/`，经 native 页挂进门户；`web/core/` 与 `web/ui-native/flow/` 为镜像双份）现状：

| 页面 | 对注册表的用法 | 代码位置 |
| --- | --- | --- |
| 待办中心 | 只**读**单条：办理任务时按 formKey 调 `GET /forms/{key}` 解析页面坐标，查不到退回内置 FORM_MAP 兜底 | `web/core/todo-center.js:45-59` |
| 流程设计工作台 | 唯一**写**入口，但是副作用：节点属性里「编辑表单工作台」保存工作区节点成功后自动 POST 一条 `kind='workspace'` 绑定 | `web/core/design-workbench.js:1809-1826` |

### 二、问题

1. **`GET /api/flow/forms` 列表接口无任何前端消费**——没有绑定列表页、没有新建/编辑表单。
2. **非 workspace 绑定（html / native）无处维护**——只能改 `seed_form_bindings()` Rust 代码重编译，
   或手写 SQL 插库；设计工作台的自动注册不覆盖这两种 kind。
3. **运行期纠错无入口**——绑错 formKey / 改 `console`、`pk_field`、`biz_table` 等字段只能进库改，
   待办中心有 FORM_MAP 兜底掩盖部分错误，问题更晚暴露。

与 todo-center.js:38 的设计注释（「接新表单只需配一行，不改前端」）相悖——「配这一行」的动作没有 UI 承载。

### 三、演进方案（待排期）

**方案 A · 流程菜单下加 native 管理页（推荐）**

在流程菜单新增一个 native 管理页（列表 + 新建/编辑表单），直接对齐上述三个接口：列表页展示
formKey / kind / 标题 / DAM 归属 / 目标坐标，编辑表单按 kind 联动显示 workspace_node、html_page、
native_page 等字段。零后端改动，纯前端新增。

**方案 B · 并入流程设计工作台页签**

在 design-workbench 加「表单注册表」页签。入口更聚焦（表单绑定本就是流程设计的一部分），但工作台
已有 BPMN 画布 / 变体 / 大纲等多视图，再挂一页签复杂度偏高。
