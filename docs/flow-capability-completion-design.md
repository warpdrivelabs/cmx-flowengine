## 1. 定位与铁律

延续既有 `designer-design.html` 的核心约束——**设计器产物 = 引擎输入**。本方案是它的**续篇**：设计器骨架已落地(阶段 0–5 完成)，本方案补的是"骨架之上的血肉"——把引擎已有/将有的每个能力，都做成可视化可配置项。

四条原则不变：

- **标准优先**：画布用 bpmn-js，不自研；新增能力优先走 BPMN 标准元素，标准表达不了的才用 `cmx:` 扩展属性。
- **契约驱动**：设计器可配属性 ⊆ 编译器可解析属性。任何一端加能力，另一端同步。这是全案最硬的约束。
- **复用既有**：角色/岗位/组织选择器拉 IAM；表单接 cmx-form/DOC/DCT;工作台用 native-pages 四区范式;身份内建模块复用 cmx-database-pg。不重造。
- **专业健壮**：校验前置(画布实时诊断 + 保存前 compile 试编译 + 后端 topology 三道闸)、定义带版本、草稿/发布分离、每步可撤销。

> **一条新增铁律：外部依赖零假设。** 独立流程微服务的设计判据是"流程库里永远不会出现一张 user/role/org/form 表"(见 `standalone-microservice-design.html:132`)。本方案**尊重该判据**——身份走"外接为默认"，内建身份模块是**可选插件**(独立命名空间表 + 同一 `AssigneeResolver` trait),绝不把主数据焊死进引擎核。

## 2. 现状盘点：evidence-backed 硬事实

以下每条都经源码直接探证，非推测。

### 2.1 引擎节点与事件

- **NodeKind 仅 8 种**：Start / End / UserTask / ServiceTask / Exclusive(排他网关) / Parallel(并行网关) / BoundaryTimer / CallActivity(`ir.rs:28-57`)。
- **网关缺 3 种**：inclusive(包容)、eventBased(事件)、complex(复杂)——编译器 `compiler.rs:445-462` 黑名单**显式拒绝**,连同 subProcess/scriptTask 一并挡回。
- **事件仅边界定时器**：`timeDuration` only,且只能挂 userTask。缺 message/signal/error/条件/补偿/中间抛接事件/timer-start。
- **multiInstance**：会签(并行)/或签(顺序)仅 `collection` 驱动,**无票签/权重**;completionCondition 只能读计数(过半/驳回)。

### 2.2 表达式引擎(分支条件的地基)

- 自研零依赖(`expr.rs`),支持 `|| && ! 比较 算术 ()`。
- **无函数调用**;**点号属性被当平坦 key**——`order.amount` 不会解析成"order 对象的 amount 字段",而是查一个名为 `order.amount` 的平坦变量,嵌套路径实际不生效。
- `eval_condition`(`expr.rs:34-48`)是**唯一外露面**——这是补齐条件能力最关键的"单点可换"接缝。

### 2.3 流程变量

- **仅实例级一层**,JSON `Value` 无类型系统,无局部/任务级作用域。
- 无"设计态变量声明"——变量是运行时随手 set 出来的,设计器无从知道有哪些变量、什么类型 → 直接导致分支条件构造器"无变量可选"。

### 2.4 运行时动作

- **已实现**:start / complete / claim(认领) / transfer(转办) / delegate(委派) / add_sign(加签,事前事后) / cancel。
- **缺**:退回/驳回/取回/自由跳转/挂起恢复/催办/已阅/消息提醒/超时处理三选一(自动通过/转办/提醒)。

### 2.5 前端设计器(`design-workbench.js`,1420 行)

- bpmn-js 已集成,实为 3 区(非严格 4 区)。
- 属性面板仅覆盖 5 类元素;**UserTask 就 6 个裸文本框**(assignee / candidateGroups / formKey / formMode / formFields),手打 `role(FINANCE)` 无联动。
- **分支条件仅 1 个 `${expr}` 文本框**,无可视化构造器;写回走 `moddle.create('bpmn:FormalExpression',{body})`(`:1196-1199`)。
- 网关只有名称字段,**无 default-flow(默认流)UI**。
- **无流程变量面板**;无会签/超时/抄送/按钮权限/边界定时器配置 UI。
- 校验(`doValidate:1263`)是假的——只查有没有 "process" 字样。
- 子流程配置最完整(calledKey + 组织绑定对话框 `:446-481`),但**无变量映射 UI**。
- 发布需重启引擎。

### 2.6 组织/角色/用户/岗位

- **引擎不建表**:DDL 里没有 cmx_org/cmx_role/cmx_user/cmx_position。
- 纯外接:pg 模式读 IAM 库(`resolver.rs`/`subflow_router.rs` 直读 `cmx_role`/`cmx_user_role`/`cmx_position`/`cmx_user_position`/`cmx_org`),http 模式 POST `{base}/identity/resolve`。
- **无任何主数据 CRUD**:只有只读 `/orgs` `/users` 端点,没有增删改页面。
- 这是**刻意设计**,非缺陷(见 §1 铁律)。

### 2.7 上线面 vs 目标面

- 当前上线仅 **2 个菜单页**(设计工作台 + 待办中心) vs 清单 **53 功能点**。
- 约 18 张 `cmx_flow_*` 表,缺:流程分组、审批定义分离、异常表、8 类操作日志、委托配置、补偿、重点人员。

## 4. 五大解决方案

### 决策① 身份双模：外接为默认 + 可选内建身份模块

**问题**：用户要"组织机构/角色/用户/岗位等常规功能",但引擎判据是"流程库永不建 user/role/org 表"。二者不冲突——**分层解决**。

```
                    ┌─────────────────────────────┐
   AssigneeResolver │  同一 trait,两种实现        │
   (引擎唯一外露面) │                             │
                    ├──────────────┬──────────────┤
        默认(零回归)│ Pg/HttpResolver│ LocalResolver│ 可选插件
                    │ 读外部 IAM 库  │ 读内建身份表 │
                    └──────────────┴──────────────┘
                                          │
                          ┌───────────────┴───────────────┐
                          │ 内建身份模块(独立命名空间)     │
                          │ fid_org / fid_role / fid_user  │
                          │ / fid_position + CRUD 四区工作台│
                          └───────────────────────────────┘
```

- **默认**：不装内建模块时,行为**零回归**——继续外接平台 IAM。独立部署且无外部 IAM 时,才启用内建模块。
- **内建模块**：独立命名空间表(`fid_*` 前缀,绝不叫 cmx_user),配套"组织机构/角色/用户/岗位"四个 native-pages 四区工作台(对标字典维护工作台),后端 `LocalResolver` 实现同一个 `AssigneeResolver` trait。
- **切换**：环境变量 `FLOW_IDENTITY_MODE = external(默认) | local`。引擎核**一行不改**——只是注入不同的 resolver 实现。
- **关系型解析扩展**(A10)：resolver 增加策略——"部门领导""发起人上级""发起人本人""委托人领导""岗位 + 组织交叉"。这些是纯 resolver 逻辑,external/local 两模式各自实现。

> 这样既满足用户"要有这些常规功能",又不违背"引擎核不焊主数据"的判据——**主数据是插件,不是核**。

### 决策② 分支条件可视化行式构造器

对标清单 A7:条件不是让用户手写 `${...}`,而是**一行一条件,可视化拼装**。

```
┌───┬────────┬──────────────┬────────┬──────────┬──────┐
│ ( │  函数   │    变量       │ 比较符 │  比较值   │  )   │  连接符
├───┼────────┼──────────────┼────────┼──────────┼──────┤
│   │        │ order.amount  │   >    │  10000   │      │  AND
│   │ DAYS() │ apply.date    │   <=   │  30      │      │
└───┴────────┴──────────────┴────────┴──────────┴──────┘
        ↓ 编译
  ${order.amount > 10000 && DAYS(apply.date) <= 30}
```

- **变量列**：下拉,数据源 = 流程变量声明(决策③)+ 表单字段。不再手打。
- **比较符**：`> >= < <= == != 包含 属于 为空`。
- **比较值**：常量,或"另一个变量"(切换)。
- **函数列**：内建函数库(`DAYS/NOW/AGE/SUM/CONTAINS/...`)下拉。
- **括号 + 连接符**：拼复合条件,可视化不会拼出语法错。
- **底层**：扩展 `eval_condition`(唯一外露面)——补**函数注册表** + **嵌套路径解析**(让 `order.amount` 真的取 order 对象的 amount)。构造器产物仍是标准 `${expr}`,存进 BPMN,引擎照吃。
- **默认流(default-flow)UI**：网关属性面板加"默认分支"下拉(选一条出边作 default),写回 BPMN `default` 属性。

### 决策③ 流程变量:设计态一等公民 + 类型系统

**根因**:变量从"运行时随手 set"升级为"设计态先声明"。没有声明,条件构造器就没有变量可选、表单就没法映射。

- **流程级变量声明区**(画布空白处属性面板一个页签):声明 `name / 类型 / 默认值 / 作用域 / 来源`。
  - 类型:`string / number / boolean / date / enum / object / array`。
  - 来源:`手工 / 表单字段 / serviceTask 返回 / 发起参数 / 子流程回传`。
- **表单字段映射**(E1):formKey 绑定后,把表单字段一键"提升"为流程变量 → 直接进变量池 → 条件构造器可选。
- **类型系统落地**:变量声明存 sidecar(`cmx_flow_var_schema`,按定义 + 版本)。运行时仍是 JSON Value,但**设计态有 schema**,用于:① 条件构造器变量下拉 ② 类型校验 ③ 表单联动。
- 引擎侧**零破坏**:schema 是设计态元数据,运行时按需做软校验;不声明也能跑(向后兼容)。

### 决策④ 属性面板分页签 + IAM 联动选择器

把"6 个裸文本框"重构成**分页签专业面板**。以 UserTask 为例:

```
┌─ UserTask 属性 ────────────────────────────┐
│ [基本] [办理人] [审批方式] [表单] [超时] [抄送] [按钮] [监听]
├────────────────────────────────────────────┤
│ 办理人页签:                                  │
│   ○ 指定人员   [选人 ▾] ← 拉 IAM/内建身份    │
│   ○ 角色       [选角色 ▾]                     │
│   ○ 岗位       [选岗位 ▾]                     │
│   ○ 部门领导   [层级 ▾]  ← 关系型解析         │
│   ○ 发起人本人 / 发起人上级                    │
│   ○ 表达式     [变量 ▾]                       │
├────────────────────────────────────────────┤
│ 审批方式页签: ○单人 ○或签 ○串行会签 ○并行会签 │
│   ○票签[通过比例 __%] □超时自动[通过/转办/提醒]│
└────────────────────────────────────────────┘
```

- **联动选择器**:选人/角色/岗位/组织不再手打 code,而是弹出 IAM 树/列表(external 拉平台 IAM,local 拉内建身份),选中写回 `role(FINANCE)` 表达式。**这是"人与组织"维度的可视化,直击用户痛点**。
- 各元素页签集:
  - UserTask → 基本/办理人/审批方式/表单/超时/抄送/按钮权限/监听器。
  - Gateway → 基本/条件构造器/默认流。
  - CallActivity → 基本/子流程/组织路由矩阵/变量映射(决策⑤)。
  - ServiceTask → 基本/服务(URL/delegate)/入参出参映射。
  - BoundaryEvent → 基本/定时器(周期/日期/持续)/中断性。
- 面板改动 ↔ bpmn-js moddle 双向绑定;`cmx:` 扩展属性需注册 moddle 扩展描述符(当前存 `$attrs`,要正式化)。

### 决策⑤ BPMN XML 窄腰不变 + sidecar

**约束**:再多的新配置,也不能破坏"BPMN XML 是前后端唯一交换格式"这条窄腰。

- **能进标准 BPMN 的**:走标准元素/属性(condition、default、multiInstance、boundaryEvent、timerEventDefinition)。
- **标准表达不了的**(cmx 特有):走 `cmx:` 扩展属性(candidateGroups 表达式、cc 抄送、calledKey、按钮权限),注册 moddle 扩展描述符正式化。
- **结构化配置**(审批定义完全体、变量 schema、组织路由矩阵):存**按节点 sidecar**——`cmx_flow_approval_def`(审批定义)、`cmx_flow_var_schema`(变量)、`cmx_flow_subflow_binding`(已有,组织路由)。sidecar 用 `definition_id + version + node_bpmn_id` 关联,与 XML 解耦。
- **好处**:XML 保持标准可移植(能被任何 BPMN 工具打开),cmx 复杂配置不污染 XML;版本化时 XML + sidecar 一起快照。

## 7. 技术风险与对策

| 风险 | 对策 |
|---|---|
| **eval_condition 扩展破坏现有表达式** | `eval_condition` 是唯一外露面,新增函数注册表 + 嵌套路径解析走**加法**,旧平坦 key 语义保留;先补充测试锁定现有行为再改。 |
| **内建身份模块与外接 IAM 语义漂移** | 同一 `AssigneeResolver` trait 双实现,契约测试保证两模式对同一输入产同一候选集;`fid_*` 独立命名空间不撞平台表。 |
| **cmx: 扩展属性 moddle 注册** | 写 moddle 扩展描述符(JSON schema)正式化 `$attrs`,bpmn.io 官方支持(camunda/zeebe 先例);P3 攻克。 |
| **sidecar 与 XML 版本错位** | 发布时 XML + 三张 sidecar(审批/变量/路由)按 `definition_id+version` 原子快照,一起版本化。 |
| **变量类型系统与运行时 JSON 冲突** | schema 是设计态软约束,运行时仍 JSON Value,不声明也能跑(向后兼容),类型仅用于设计态联动 + 软校验。 |
| **属性面板重构面大** | 分页签按元素类型增量交付,UserTask 先行(最高频),其余元素逐个补;每个页签独立可测。 |
