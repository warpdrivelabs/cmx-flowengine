# 一、多业务系统接入面（对接多个业务系统时的结构性问题）

## 001 · 出站 webhook 多业务系统接入限制

> 记录日期：2026-08-17 ｜ 复核：2026-08-21 仍存在（行号按 HEAD 重定位）。

### 一、现状（代码事实）

出站生命周期 webhook 的实现位于 `crates/cmx-flow-adapters/src/webhook.rs`，配置读取位于
`crates/cmx-flow-adapters/src/config.rs`（`WebhookConfig::from_env`）。当前能力：

| 能力 | 现状 | 代码位置 |
| --- | --- | --- |
| 多回调端点 | ✅ 支持。`FLOW_WEBHOOK_URLS` 为逗号分隔列表，每条事件 POST 给**全部** URL | `webhook.rs:137-151` `spawn_worker`（`for url in &urls`） |
| 配置来源 | ⚠️ 仅环境变量（`.env` / 进程 env），toml 未承载 | `config.rs:77-93`（纯 `std::env`） |
| 事件路由 | ❌ 无。广播模型，不带订阅过滤（无 definitionKey/事件类型维度） | 同上 |
| 签名密钥 | ⚠️ 全局唯一一把 `FLOW_WEBHOOK_SIGNING_KEY`，所有端点共用——持密钥者可向任一端点伪造事件 | `config.rs:86-92` |
| 投递方式 | ⚠️ 单后台 worker 串行消费，逐 URL 顺序 await，失败指数退避（1s/2s/4s…上限 64s，默认重试 3 次）；一个慢/挂的端点拖住全部端点 | `webhook.rs:143-149`、`deliver` |
| 持久化 | ❌ 内存 mpsc 队列（容量 1024），进程重启丢事件；队列满 `try_send` 失败仅 warn 丢弃 | `webhook.rs:141`、`154-160` |
| 死信 | ❌ 重试耗尽（默认 3 次）后事件直接放弃（warn「重试耗尽，放弃」），无死信表可补偿；worker JoinHandle 被 spawn 后丢弃，无优雅关闭信号 | `webhook.rs:210-213` |

### 二、多业务系统场景的短板

1. **无事件路由（广播 + 接收方自行过滤）**：每个端点收到**所有**系统的事件（含 businessKey 与单据变量投影）——信息泄露面 + 无效流量。MDM 侧靠回调入口五规则过滤自保（`cmx-container/cmx-mdm-api/src/handlers/flow_cb.rs`），但每个新接入方都得重做一遍过滤，容易漏。
2. **签名密钥全局唯一**：跨团队/跨安全域接入不成立。
3. **串行投递互相拖累**：单 worker 串行 `for url` await，一个慢端点（含最长 64s 退避）拖住所有端点；队列随事件量打满后开始静默丢。
4. **内存队列重启丢事件**：MDM 有懒同步自愈兜底（回调失败 5 分钟窗口内查询时回查引擎状态），其他接入方无此兜底前需知悉。

### 三、演进方案（已论证，待排期）

**方案 A · 配置层多 target（推荐首版）**

toml 改为数组，每个 target 独立密钥 + 可选 definitionKey 订阅过滤 + 每个 target 独立 worker（互不拖累）；不配 targets 时回退现有单配置，兼容现状：

```toml
[[webhook.targets]]
urls = "http://127.0.0.1:8080/api/mdm/flow/callback"
signing_key = "mdm_flow_hook_dev_secret"
definition_keys = "mdm_cr_approval"   # 空 = 订阅全部

[[webhook.targets]]
urls = "http://oa-system/flow/callback"
signing_key = "oa_own_secret"
```

同时补 toml 承载：flow-server 的 `apply_toml_env()`（`crates/cmx-flow-server/src/main.rs`）已有「toml 段 → `set_var` 注入 FLOW_*（env 未设时）」通道；加 `[webhook]` / `[[webhook.targets]]` 段即可。改动集中三处：`config.rs` + `webhook.rs` + `main.rs`。规模小。

死信补齐（可与方案 A 并行或后续）：事件先落 outbox 表再投递，投递成功标记、失败留行；运维台补「失败事件重发」入口（联动 012）。

**方案 B · 注册订阅模型（完整形态，暂无诉求）**：`POST /api/flow/webhooks` 注册（URL + 密钥 + 订阅定义列表）落 pg 配管理页面。适用于多租户/动态接入，当前不做。

### 四、相关决策记录

- **2026-08-17**：限制记录在案；MDM 侧暂不修改（五规则过滤 + 懒同步兜底已防御），演进按方案 A 实施，待排期。

## 003 · API Key 无按业务系统的授权边界与审计

> 记录日期：2026-08-20 ｜ 复核：2026-08-21 仍存在。

### 一、现状（代码事实）

- **key → 租户，到此为止**：`FLOW_API_KEYS="k1:tenantA,k2:tenantB"` 解析为 `HashMap<key, tenant>`（`crates/cmx-flow-app/src/auth.rs:104-123`），命中后建 `TenantCtx::new(tenant) + roles=["service"]`（auth.rs:144-166）。key 上没有 scope、没有可发起 definitionKey 白名单、没有可调用端点限制。`start_instance` 对 `definition_key` 零校验。
- **key 无审计字段**：key 建立上下文后即被丢弃，`TenantCtx` 只有 tenant/user/roles 三字段（tenant.rs:24-31）——日志/webhook/意见留痕里所有系统 M2M 调用都是同一个匿名 "service"，无法回答「哪个系统在调」，也无法按系统限流/吊销（全仓 grep "audit" 仅命中测试夹件）。
- **实际部署只有一把共享 key**：`flow-server.toml` 与 `deploy/docker-compose.yml` 的 `FLOW_API_KEYS` 均只配一条（平台 key → default 租户），MDM/财务/OA 全经它进来；一动全动。
- **委托令牌验签失败仅降级不拒绝**（auth.rs:203-216）：key + 坏委托令牌 = 纯服务身份，可继续 start/cancel/jump/set-variables 等端点（complete 已有 T0b 拒绝），事后留痕无办理人。

### 二、多业务系统场景的影响

拿到任何一把 key = 拿到**所有业务系统所有流程**的发起/读取/干预权限（结合 004/006 即现实可利用）；跨安全域共享密钥不符合最小权限；故障与安全事件无法按调用方系统溯源。

### 三、演进方向

key 声明扩展为 `key:tenant:system` 或结构化表（key、system、allowed_definition_keys、可调用端点类别）；`TenantCtx` 增加 `system` 字段全链路透传（日志/事件/意见留痕）；`start_instance` 校验 definitionKey ∈ key 白名单；委托令牌验签失败按端点分级（涉及身份的动作拒绝、纯查询降级）。配置形态与 001 方案 A 的 toml 化同批推进。

## 004 · 用户身份参数化——残余越权面

> 记录日期：2026-08-20 ｜ 复核：2026-08-21 部分解决。complete/cancel/withdraw 三端点已补 T0b 服务端授权（见下），其余越权面未动。

### 一、已补齐的部分（2026-08-20，92f4917）

- `complete_task`（handlers.rs:1049-1074）：有用户身份时须为该任务 assignee 或候选（物化候选表），否则拒绝；auth 中间件已生效却无身份 → 拒绝；宿主未挂 auth → 放行（`operator` 仍取请求体但仅作留痕）。
- `cancel_instance`（handlers.rs:751-769）：有身份时须为发起人（`variables.initiator`）。
- `withdraw_instance`（handlers.rs:794-818）：同上且 fail-close。

### 二、仍存在的部分（代码事实）

| 端点 | 问题 | 代码位置 |
| --- | --- | --- |
| `GET /tasks/my?assignee=…` 及 `/todos/initiated|cc|done?user=…`、`/withdrawable?user=…` | 用户标识来自 query 参数且不与 `tenant::current_user()` 比对（注释自认「F2 允许 query 传值便于 curl 验证」）——传谁查谁 | handlers.rs:1560-1562、1596-1630、1640+、826-843 |
| claim / transfer / delegate / addsign / reject | 操作者（`user_id`/`from_user`/`to_user`）全部来自请求体，不校验 current_user 是否为任务 assignee/owner；转签台账记录的 from_user 是客户端自报值 | handlers.rs:1146-1156、1168-1185、1502-1519、1536-1554、1206-1242 |
| `GET /instances/{id}`、`/{id}/variables`、`/{id}/comments`、`/{id}/biz` | 按 id 载入即返回，不校验请求者是否发起人/办理人/候选/抄送人；variables 是业务系统塞入的任意业务数据 | handlers.rs:707-718、852-894 |
| `GET /users`、`/orgs` | 全量吐 IAM 用户/组织表（LIMIT 200 无过滤），共享端点跨系统暴露通讯录 | handlers.rs:1816-1845、1894-1910 |
| 鉴权默认值 | `FLOW_AUTH_MODE` 非 "jwt" 一律 Off（auth.rs:63-66），off 模式 `X-Tenant`/`X-User` 头直传即信任（auth.rs:180-184）；配置文件缺失/拼写错误静默落入 off 而非拒绝启动 | auth.rs、`cmx-flow-server/src/main.rs:71-88` |

### 三、多业务系统场景的影响

任何拿到 key 的系统（或 off 模式下任何人）可：枚举任意用户跨**所有系统**的待办/已办/抄送（含 businessKey、bizTable/bizId、applicant/amount 投影）；替任意用户认领/转办/委派/加签/驳回任何在途任务且审计不可信；按 id 读任意实例完整变量（跨系统业务数据泄露）。off 默认值让独立 flow-server（:8091）一次配置丢失即变成无鉴权全系统流程网关。

### 四、演进方向

1. 身份一律取服务端上下文（JWT/委托令牌解出的 current_user），query/body 的 user 参数仅运维角色可用且需显式角色（对齐 complete 的 T0b 模式，逐端点补齐）；
2. off 模式改为显式 opt-in，未知值拒绝启动（fail-fast）；
3. 实例读取按参与方（initiator/assignee/candidate/cc）过滤，或至少给跨系统读取加角色门槛；
4. `/users`、`/orgs` 收敛为按需搜索 + 字段白名单。

## 005 · 多租户/业务系统数据模型缺失

> 记录日期：2026-08-20 ｜ 复核：2026-08-21 仍存在，且新侧表与主表的不一致加深了债。

### 一、现状（代码事实）

- **运行态主表无 tenant_id / system_id**：`crates/cmx-flow-store-pg/src/ddl.rs` 的 instance（17-30）/token（41-49）/task（52-67）等全部主表无租户/系统维度列，实例表仅有 `org_id`；`cmx-flow-app/src/biz_link.rs:37-74`（biz_link/task_comment/form_binding）同样无。
- **不一致加深**：92f4917 新增的侧表反而都带了 `tenant_id VARCHAR(64) NOT NULL DEFAULT 'default'`——`cmx_flow_message_subscription`（ddl.rs:209）、`cmx_flow_deadletter_job`（ddl.rs:250）、`cmx_flow_hi_activity`（ddl.rs:266）——新旧两代表并存，列级隔离口径分裂。
- **single 模式是默认且租户头失效**：`FLOW_TENANCY` 非 "multi" 即 single（tenancy.rs:40-43），single 下 `flow_db_id()` 无条件返回 `FLOW_DB_ID`（tenancy.rs:52-58）——无论 `X-Tenant`/JWT claim 是什么都写同一个库。隔离完全依赖 db-per-tenant（multi 模式），且隔离维度只有租户、没有业务系统（同租户内多系统仍全混）。
- **`FLOW_DB_ID = "fico-db"` 写死**（`crates/cmx-flow-app/src/engine.rs:37`）：默认租户库常量名绑死财务库名；所有鉴权回退路径（无 scope 后台任务、off 缺 X-Tenant、JWT 缺 tenant claim 回退）最终都落到财务库——**隔离回退方向指向了一个具体业务系统**；其它宿主接入必须先注册一个恰好叫 "fico-db" 的数据源（`cmx-flow-server/src/main.rs`）。

### 二、多业务系统场景的影响

默认部署下 MDM/财务/OA 的实例、任务、意见、单据关联物理混在同一批表里：无法按系统过滤（联动 004 的横向读取）、归档、分库迁移；`GET /instances` 等列表口径天然跨系统混排；fico-db 命名让引擎与财务系统产生假耦合。

### 三、演进方向

短期：`FLOW_DB_ID` 改为配置项（toml/env），默认值改中性名（如 `flow-default`），发布迁移说明；中期：multi 模式补租户列（新旧表对齐）+ 查询过滤，评估是否引入 `system_id` 列或以 definitionKey 前缀约定（`mdm_xxx` / `fi_xxx`）做软隔离。

## 007 · 实例写路径无并发控制

> 记录日期：2026-08-20 ｜ 复核：2026-08-21 仍存在。

### 一、现状（代码事实）

所有推进路径（complete/claim/transfer/reject/withdraw/消息唤醒/定时器触发/迁移）都是 `load_snapshot`（多条独立 SELECT）→ 内存修改 → `save_snapshot`（**七张子表全删重插**，`crates/cmx-flow-store-pg/src/store.rs:85-150` `build_save_ops`，单事务但无行版本比对——后写覆盖先写）。代表路径：complete_task（`cmx-flow-engine/src/engine.rs:930-1066`，load 936 / save 1066）、reject（1373/1450）、`trigger_due_timers`（2228/2260）、migrate（1652/1674）。DDL 中 `cmx_flow_instance` 无 version/rev 列（ddl.rs:17-30）。全仓 `FOR UPDATE` 仅一处：`acquire_async_jobs` 的 SKIP LOCKED（store.rs:539）——那是 async_job 独立侧表（DDL 注释明确它不随快照全删重插，ddl.rs:215-217），**主实例路径完全没有行锁/乐观锁**。

### 二、影响

同一实例两个任务并发 complete（两用户同时提交，或 LB 分到不同节点）时，后保存者以旧快照全量覆盖前者——**办结状态被抹回、令牌回退**，流程状态错乱且无告警。并发 claim 两人都收到成功响应。用户刚标记的抄送已读（`mark_cc_read` 独立 UPDATE）会被下一次旧快照 save 回滚为未读；转签台账/候选池同理（只增不改的实体不该走全删重插）。写放大随任务数线性增长。

### 三、演进方向

`cmx_flow_instance` 加 `version` 列（乐观锁），save 前比对版本冲突即拒绝重试；cc 已读等**旁路小写**改为独立表或从快照 save 中剔除；async_job 侧表「不随快照重插」的模式可推广到转签台账/意见。

## 009 · 事务边界与静默吞错

> 记录日期：2026-08-20 ｜ 复核：2026-08-21 仍存在。

### 一、现状（代码事实）

- **发起 + bizLink 绑定两事务**：`start_process_org`（事务 1）成功后 `link_biz_to_instance`（独立 INSERT，事务 2）失败才补偿 `cancel_process`，但补偿结果被 `let _ =` **忽略**（handlers.rs:664-682，677-680）——DB 抖动时产生孤儿实例（实例在跑、单据无关联、客户端已收到失败），业务侧无从对账。
- **审批意见留痕静默丢失**：complete/reject 办结成功后 `let _ = insert_task_comment(...)`（handlers.rs:1091-1103、1229-1239），DB 失败**连 warn 日志都没有**（`insert_task_comment` 内部也无日志，biz_link.rs:234-264）；意见是合规审计数据，任务已办结不可补。
- **TaskCreated 无差别重复广播**：办结后遍历快照**全部 tasks** 逐个 emit TaskCreated（handlers.rs:1106-1135），仅跳过刚办结的 task_id（1121），**无 `!completed` 过滤、无「新产生」判定**——并行分支既有待办被重复广播，甚至已办结仍留在表里的历史任务也会被误发（1117-1119 注释自认）。

### 二、演进方向

发起 + 绑定合入单事务（或补偿失败必须 error 日志 + 告警指标）；意见写库失败至少 warn + 计数指标（联动 013）；事件 emit 只针对**本次 save 新建**的任务（对比前后任务集 diff，或 `!completed` 过滤）。
