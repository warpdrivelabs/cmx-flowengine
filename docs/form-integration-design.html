cmx-flow × 表单系统 集成方案

表单如何接进流程 · 表单数据如何进出流程 · 待办任务如何打开对应表单

设计方案不动代码对齐现有契约窄腰不变

一句话结论：三个问题都能在不改引擎窄腰的前提下解决。流程引擎的 Variables（JSON KV，落 jsonb）天然就是表单数据的载体；表单系统已有按 ctx.props 参数打开页面的成熟先例（报表设计器就是这么开的）；待办打开表单 = 用同一套 openTab(workNode) 机制，把 {formKey, taskId, bizRef} 作为 props 传给表单页。整套集成的新增面很薄：一个「表单绑定」约定 + 一个「单据↔实例」关联表 + 一个「我的待办」跨实例查询端点。

1 · 定位：谁负责什么，窄腰在哪 先划清边界

流程引擎管「谁在什么时候该干什么」，表单系统管「干这件事时填/看什么数据」。两者通过一个极窄的契约耦合，各自独立演进。

流程引擎（cmx-flow）负责

  • 流转编排：节点、网关、会签、子流程、定时器
  • 任务生命周期：产生待办 → 办理 → 令牌推进
  • 办理人解析：角色/岗位/组织 → 真实用户
  • 流程变量 Variables：实例作用域的动态 KV

表单系统（native/html-pages）负责

  • 字段渲染：主从表、明细、下拉、校验
  • 业务数据读写：/api/<域>/<表>/search 载入、POST 保存
  • 数据模型：CmxMasterSlave 协调器（多级主从 + 汇总）
  • 页面契约：initPage / getState / isDirty / validate
窄腰契约（只有这些跨界）：
  1. 节点 → 表单：userTask 上一个 formKey（哪张表单）+ 可选 formMode（只读/可编辑/仅审批）。
  2. 数据 ↔ 流程：表单产出/消费一份 JSON，进出流程时映射到 Variables；重数据留在业务表，流程只存引用 + 关键决策字段。
  3. 待办 → 表单页：一个 props = {formKey, taskId, instanceId, bizTable, bizId, mode}，经现有 openTab 机制传入表单页。
这三条之外，引擎不认识表单、表单不认识 BPMN——可各自替换。

2 · 现状盘点：两侧各有什么、缺什么 代码核实

流程引擎侧

能力状态位置 / 说明

办结带变量已有complete_task(instance_id, task_id, vars) 把提交变量 merge 进实例

盘点结论：大头都在。引擎的变量/业务键/属性解析、表单的 props 开页/数据读写/页面契约——四大支柱全部现成。缺的是把它们串起来的三根线（formKey 绑定、单据↔实例关联、我的待办查询），以及两处「薄」需要补厚（通用变量入参、审批态表单皮肤）。没有一处需要动窄腰 compile(xml)→ProcessDefinition。

3 · 核心模型：单据 · 变量 · 表单三者关系 最关键的一节

先厘清一个容易含糊的问题：表单数据到底存在哪——存流程变量里，还是存业务表里？答案是分层，这决定了后面所有设计。

① 业务单据（重数据）

存在业务表：cf_*(dct) / doc 表

请款单的全部明细行、附件、几十个字段。数据的家在这里，流程只持有它的引用（表名 + 主键）。

② 流程变量（决策数据）

存在实例 Variables(jsonb)

驱动流转的少量关键字段：amount（走哪条网关）、applicant、lastDecision、会签 approvers[]。只放条件/路由要用的。

③ 表单（视图）

native/html-page，运行期渲染

把①的业务数据渲染出来给人看/填；把人的输入写回①，把关键字段同步给②。表单是①②的读写窗口，自身不持久化。

设计红线：不要把整张单据塞进流程变量。流程变量是「作用域动态 KV」，用来算网关、驱动会签；单据是「行列强类型存储」，用 CmxMasterSlave 管主从汇总。两者关注点不同（引擎注释里已明确 Variables 不复用 DataValue）。把明细塞进变量会让 jsonb 膨胀、条件表达式失焦、审计困难。正确做法：单据留业务表，变量只存「引用 + 决策字段」。

三者的绑定关系

┌─────────────────────────────────────────────────────────────┐ │ 流程实例 Instance │ │ ├─ business_key = "PAY-2026-0042" ← 人读的单号 │ │ ├─ variables (jsonb) ← 决策数据 │ │ │ { amount: 85000, applicant: "u_1001", │ │ │ bizTable: "cf_pay_request", ← 单据引用(表) │ │ │ bizId: "PR8842", ← 单据引用(主键) │ │ │ lastDecision: "approve" } │ │ └─ tasks[] ─ 每个 userTask 带 formKey ─┐ │ └────────────────────────────────────────┼─────────────────────┘ │ formKey="pay.review" ▼ ┌─────────────────────────────────────────────────────────────┐ │ 表单页 (native-page: portal.form.runner) │ │ props = { formKey, taskId, instanceId, bizTable, bizId, │ │ mode:"task" } │ │ ├─ 载入: GET /api/<域>/cf_pay_request/search?id=PR8842 │ │ │ → ms.setFlatData(...) ← 从业务表读① │ │ ├─ 渲染: 只读审阅 + 审批意见栏 (mode=task) │ │ └─ 办结: POST /api/flow/tasks/{taskId}/complete │ │ { instanceId, variables:{ lastDecision, comment }} │ └─────────────────────────────────────────────────────────────┘

4 · 问题一：表单如何绑定到流程节点 formKey 约定

业界（Flowable/Camunda）的标准做法是 userTask 上一个 formKey 属性。我们沿用，且复用现有编译器的前缀无关取属性能力——零新解析框架。

4.1 BPMN 侧：userTask 加 formKey

<!-- 设计器在节点属性面板配置，编译时被 local_attr 读取 -->
<userTask id="review" name="财务复核"
          flowable:assignee="role(finance)"
          cmx:formKey="pay.review"          <!-- 哪张表单 -->
          cmx:formMode="approve"        <!-- edit|readonly|approve -->
          cmx:formFields="amount,comment" <!-- 该环节可写字段(可选白名单) -->/>
编译改动（薄）：在 cmx-flow-model 的 UserTask IR 加三个可选字段 form_key / form_mode / form_fields；在 cmx-flow-bpmn/compiler.rs 的 userTask 解析里加三行 local_attr(node, "formKey") 等。——与现有 assignee/candidateGroups 解析完全同构，无新机制。

4.2 起点表单（发起态） vs 环节表单（办理态）

发起表单 startForm环节表单 taskForm
配在哪process 级 cmx:startFormKey，或流程定义元数据userTask 级 cmx:formKey
什么时候开用户「新建请款单」时办理人点开待办时
典型 modeedit（填单）approve（审阅+意见）或 edit（补充信息）
产出建业务单据 + 起流程实例写审批意见 + 办结任务

4.3 formKey → 具体表单页的解析

formKey 是逻辑名，不直接等于某个 native-page id——这样同一流程在不同部署可换皮肤。解析走一张小注册表（或复用菜单/DAM 元数据）：

// 表单注册表（新增一张轻表 cmx_flow_form_binding，或用 JSON 配置）
{
  "pay.review": {
    nativePage: "portal.form.runner",   // 通用表单宿主页(见 §6)
    bizTable:   "cf_pay_request",      // 绑定的业务表
    domain: "fi", app: "cmxfico", module: "gl",
    title: "请款单复核"
  }
}

解析发生在「打开待办」时（§6），把 formKey 换成 {nativePage, bizTable, …} 再拼 props。

5 · 问题二：表单数据如何进出流程 双向映射

数据流有四个关口：发起时进、办理时读、办结时进、流转时用。每个关口都落在既有能力上。

5.1 发起：表单 → 建单据 → 起流程（数据入口）

1
用户在发起表单填单、点「提交」。表单调 ms.exportKeyValue() 得到整张单据 JSON。
2
先存业务单据：POST /api/<域>/<表>/save（现有 dct/doc 写端点），拿回单据主键 bizId。
3
再起流程：POST /api/flow/instances，body 带通用 variables： 
{
  definitionKey: "pay_approval",
  businessKey:   "PAY-2026-0042",
  orgId:         "d_fin_sh",
  variables: {                    // ← 只放决策/引用字段
    amount: 85000, applicant: "u_1001",
    bizTable: "cf_pay_request", bizId: "PR8842"
  }
}
4
回写关联：把 instanceId 写回业务单据的 process_instance_id 列（单据↔实例双向可查）。
需要补厚的点：StartReq 目前是 demo 硬编码 applicant/amount。改为通用形态：{definitionKey, businessKey, orgId, variables: Value}，handler 里 Variables::from_json(req.variables) 直接喂引擎（引擎早已接受任意 Variables，只是 API 层入参没开放）。纯 API 层改动，引擎零改。

5.2 办理：读实例变量 + 读业务单据（数据出口）

办理人打开待办时，表单页需要两份数据：

  • 业务单据（看什么）：用 props 里的 bizTable/bizId 调 /search 载入 → ms.setFlatData()。
  • 流程上下文（谁提的、走到哪、前面怎么批的）：调 GET /api/flow/instances/{id} 拿变量 + 任务链 + 历史意见。

5.3 办结：意见/决策 → 流程变量（数据入口）

// 办理人点「同意/驳回」，表单收集意见，办结任务
POST /api/flow/tasks/{taskId}/complete
{
  instanceId: "inst_77",
  variables: {                    // ← merge 进实例变量
    lastDecision: "approve",      // 驱动后续网关
    comment: "金额属实，同意付款"   // 留痕
  }
}

引擎的 complete_task(instance_id, task_id, vars) 已经 merge 变量——只需把 CompleteReq 从 decision: Option<String> 扩为通用 variables: Value。若该环节也改了单据（如补充字段），表单先 POST /save 更新业务表，再办结。

5.4 流转：网关/会签读变量（数据消费）

无需任何改动——这是引擎既有能力：${amount > 50000} 走总监审批、approvers[] 驱动会签、${lastDecision == 'reject'} 打回。表单办结时写进变量的值，流转时自动被读。

数据流小结：四个关口，两个入口（发起 §5.1、办结 §5.3）走 variables 进引擎，两个出口（办理 §5.2、流转 §5.4）从实例/业务表读。引擎侧唯一改动是把两个 Req 的入参从硬编码字段改成通用 variables 对象——引擎内核完全不动。

6 · 问题三：待办任务如何打开表单 复用 openTab 先例

这是三个问题里最「有现成答案」的——报表设计器打开一张「特定 org+period 的报表」用的就是这套机制，我们照搬。

6.1 待办中心（新页）

一个 native-page portal.flow.todo-center，四区工作台：

  • explorer：待办分类（我的待办 / 我发起的 / 抄送我的 / 已办），按流程/组织过滤。
  • content：待办列表（单号、流程名、当前环节、发起人、到达时间、紧急度）。
  • property：选中待办的流程轨迹缩略（走到哪、前面谁批的）。

数据来自新增的「我的待办」端点（现在只能按实例逐个查，缺跨实例聚合）：

GET /api/flow/tasks/my?assignee=u_1001&kind=todo
// 返回该用户所有未办结任务（跨实例），每条带 formKey + bizRef
{ tasks: [ {
    taskId, instanceId, businessKey, definitionName,
    nodeName: "财务复核",
    formKey: "pay.review",        // ← 从定义带出
    bizTable: "cf_pay_request",   // ← 从实例变量带出
    bizId: "PR8842",
    applicant, amount, arrivedAt, urgent
} ] }

6.2 点开待办 → 开表单页（照搬报表设计器）

1
用户点一条待办。前端拿这条待办的 formKey，查表单注册表(§4.3)解析出 {nativePage, bizTable, …}。
2
拼 workNode + props（与 openReportDesigner 逐字同构）： 
const props = {
  formKey: "pay.review", mode: "task",
  taskId, instanceId, bizTable, bizId
};
const workNode = {
  id: `flow-task-${taskId}`, type: "workspace-node",
  caption: `${businessKey} · ${nodeName}`,
  workspace: {
    params: props,
    content:  { views:[ formView("content",  props) ] },
    property: { views:[ formView("property", props) ] }  // 流程轨迹+意见
  }
};
openTab(workNode);   // ← 现有全局机制(window/parent/top 探测)
3
表单页在 mount 读 props（propsOf(ctx) = ctx.props ?? ctx.host.__props），按 mode="task" 分流：载入业务单据 + 拉流程上下文 + 渲染审批意见栏。

6.3 通用表单宿主 vs 专用表单页

方案 A：通用宿主 portal.form.runner

一个页，按 props.formKey 动态载对应字段定义（复用 dct/doc 的字段元数据）渲染。一页托管所有表单。

优点：接一张新表单零前端开发（配 formKey + 字段元数据即可）。适合标准主从表单据。

方案 B：专用表单页

复杂表单（如带 FlexibleCombination、特殊交互）仍写独立 native/html-page，注册表把 formKey 指向它。

优点：表达力不受限。缺点：每张表单一份页。两方案共存——标准的走 A，特殊的走 B。

关键洞察：「打开待办表单」不需要发明任何新机制。openTab(workNode) + workspace.params/props + 页内 propsOf(ctx) 这条链已被报表设计器验证过（一个报表按 code+version 开独立设计器 tab）。待办开表单只是把 props 从 {reportCode, version} 换成 {formKey, taskId, bizId, mode}。

9 · 分阶段交付 每阶段独立可验

F1 数据管道打通（后端）

  • StartReq/CompleteReq 改通用 variables
  • 业务表加 process_instance_id + 回写
  • curl 验证：起流程带任意变量 → 办结带任意变量 → 网关正确分流

价值：不碰表单也能证明「表单数据能进出流程」。

F2 formKey 绑定 + 我的待办端点

  • UserTask IR + 编译器加 formKey 解析
  • GET /flow/tasks/my 跨实例聚合，任务 JSON 带 formKey/bizRef
  • 设计器属性面板加「绑定表单」选择器

价值：流程「知道」每个环节该开哪张表单。

F3 待办中心 + 打开表单

  • portal.flow.todo-center 四区
  • 点待办 → openTab(props) → 表单页（先接一张真实表单，如请款单）
  • 办理态：只读审阅 + 意见栏 + 办结

价值：端到端跑通一条真实审批链。

F4 通用表单宿主 + 发起态

  • portal.form.runner 按 formKey 动态渲染
  • 发起表单「提交起流程」标准动作
  • 表单注册表 + DAM 归属打通

价值：接新表单从「写页」降为「配 formKey」。

推进建议：严格按 F1→F4。F1 纯后端、curl 即可验，是地基；F2 让定义带上表单绑定；F3 打通「待办→表单→办结」这条最核心的人机回路（先用一张手写表单）；F4 才做通用化。每阶段都不动引擎窄腰，且都能独立演示。

10 · 风险与对策 专业·精致·稳定·健壮

风险对策
数据双写不一致：单据存了、流程没起（或反之）发起动作用「先存单据(拿 bizId) → 起流程 → 回写关联」三步，失败可补偿；关联表用单据主键幂等。F1 阶段就把这条路径测透。
变量与单据字段漂移：变量里的 amount 和单据里的 amount 不一致约定单一事实源：金额等决策字段以单据为准，起流程/办结时从单据快照取值写入变量（而非人再填一遍）；变量是单据的投影，不是副本。
表单不知道自己在「办理态」props.mode 三态分流（edit/readonly/approve）；通用宿主按 mode 切皮肤，专用页自行判断。formMode 来自节点配置，设计时确定。
formKey 指向的表单被删/改名表单注册表解析失败时降级：给一个「通用只读 JSON 查看器」兜底展示实例变量 + 单据，保证待办永远能打开、能办结（不因表单缺失卡死流程）。
待办查询性能（跨实例聚合）/flow/tasks/my 走任务表的 assignee 索引 + 未办结过滤，不 load 完整快照（对齐现有 InstanceSummary 避免 N 次聚合的思路）。
权限：谁能开这张待办表单打开时校验 taskId 的 assignee/候选人是否为当前用户（复用 M4 候选人/认领语义）；表单页不自行判权，由 /tasks/my 和 complete 端点把关。
历史意见留痕每次 complete 的 comment 进变量或专门的审批意见表；表单办理态展示完整审批历史（从实例任务链 + cc 记录读）。
总纲：这套集成的精髓是「不重造、只连接」。引擎的变量系统、业务表的数据服务、表单的 props 开页机制——三根成熟支柱早已各就各位，缺的只是把它们对齐的三根细线（formKey、单据↔实例关联、我的待办查询）和两处补厚（通用变量入参、审批态表单）。窄腰 compile(xml)→ProcessDefinition 一行不动，80+ 引擎测试零回归，表单系统按既有契约扩展。业务用户看到的是「填单→提交→审批→办结」，底下跑的是标准 BPMN。
