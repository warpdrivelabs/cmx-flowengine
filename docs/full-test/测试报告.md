### 🔴 缺陷 #1（中）：`/todos/initiated`「我发起的」未按发起人过滤，跨用户泄露实例

- **现象**：`GET /api/flow/v1/todos/initiated?user=alice_init` 返回的列表中**包含他人（bob_init）发起的实例**。列表实为「全部实例按创建时间倒序取前 20」，`user` 入参被完全忽略。
- **实测证据**（Suite 11A）：
  ```
  alice's initiated list contains bob's instance? true   ← 应为 false
  alice_init list size: 20                                ← 与发起人无关的全量分页
  ```
- **根因**（已定位源码）：
  - `crates/cmx-flow-app/src/handlers.rs` `get_initiated()` 只用 `q.to_filter()` 调 `list_instances_paged(&f)`，**从未读取 `q.user`**（对比同文件 `get_cc_todos`/`get_done_todos` 均显式取 `q.user` 并下传）。
  - `crates/cmx-flow-app/src/biz_link.rs:256` `TodoFilter` 结构体**无 initiator/user 字段**；`list_instances_paged` 的 SQL `WHERE {cond}` 仅按 `definition_key`/`state`/`keyword` 过滤，**无发起人谓词**。
- **影响**：待办中心「我发起的」页签对任意用户展示**全租户所有人**发起的流程实例——功能错误 + 租户内跨用户数据可见性问题。
- **修复建议**：为 `TodoFilter` 增 `initiator: Option<String>`；`get_initiated` 把 `q.user` 灌入；`list_instances_paged` 增 `AND (variables->>'initiator') = '{initiator}'`（发起人按约定存实例变量 `initiator`）。
- **复现**：`bash t11_anomaly_edge.sh`（断言 `S11A-initiated-filter`）。

### 🟡 缺陷 #2（低）：Swagger UI 官方地址 `/api/flow/v1/docs`（无尾斜杠）跳转丢失 `/api` 前缀 → 404

- **现象**：`GET /api/flow/v1/docs` → `303` 跳 `http://…/flow/v1/docs/`（**丢了 `/api` 挂载前缀**）→ 该地址 `404`。仅带尾斜杠的 `/api/flow/v1/docs/` 才 `200`。
- **实测证据**（FE-SWAGGER-redirect-bug）：`/api/flow/v1/docs → 303 → /flow/v1/docs/ → 404`；`/api/flow/v1/docs/ → 200`。
- **根因**：`utoipa-swagger-ui` 在嵌套 `Router` 前缀下的经典「trailing-slash 重定向不含 nest 前缀」问题。
- **影响**：低（有 `/docs/` 变通）。但对着文档给出的自然地址 `…/docs` 直接 404，影响开发者首次体验。
- **修复建议**：显式为 `/docs`→`/docs/` 配相对跳转，或用 `utoipa_swagger_ui` 的 `config` 指定绝对 `url`；OpenAPI JSON `/api/flow/v1/openapi.json`（26 端点）本身正常。

### 🟠 待商榷 #3（设计点·中）：`complete`（提交/办结）不带办理人 → 无办理人鉴权、审计留痕 `userId` 为空

- **现象**：`POST /tasks/{id}/complete` **无任何办理人入参**（body 仅 `instanceId/variables/decision/comment`）。因此：
  1. 服务端**不校验**「提交者是否为该任务 assignee/候选人」——持 API Key 者可办结任意任务；
  2. 办结意见落库时 `cmx_flow_task_comment.userId = null`（实测 Suite 11E：`complete comment userId = NULL`）——**无法审计「谁办结的」**。
- **对比**：`reject(fromUser)`、`transfer/delegate/addsign(from_user/to_user)`、`withdraw(user)`、`claim(user_id)` **都**显式带办理人。唯独最高频的 `complete` 不带。
- **影响**：委托令牌（`X-Delegated-User-Token`）模式下平台侧可知真实用户，但引擎未把它写入办结审计；纯 API Key 直连时既无鉴权也无留痕。合规/审计场景需补。
- **建议**：`complete` body 增 `operator`（或从委托令牌取 `sub`），落 `comment.user_id` 并可选校验 = 当前 assignee。

### 🟢 待商榷 #4（设计点·低）：`GET /tasks/my?kind=all` 行为等同 `kind=todo`

- **现象**：源码仅特判 `kind="claimable"`，其余（含文档暗示的 `all`）一律回落「直派待办」。实测 `todo=15, all=15`（未合并可认领）。
- **影响**：低（文案与实现不一致，非数据错误）。建议要么实现「all=直派+可认领」，要么删除 `all` 文案。

4. **数据保留**：全程未清库；所有实例/任务/台账/抄送落 PG 持久保留，脚本与流水归档，任何一条断言均可重放。
