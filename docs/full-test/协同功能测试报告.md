## 一、被测能力与架构

### M1 · 感知（presence）+ 防冲突
- **感知**：谁在线（在场头像条）、谁选中了哪个节点（远端选中紫色虚线高亮）。
- **防冲突**：草稿保存**乐观锁**——以草稿 `updated_at`（RFC3339）当 etag；保存时带 `baseUpdatedAt`，服务端比对，已被他人推进则返回冲突（`conflict:true`）**不静默覆盖**，前端弹确认框让用户自决（覆盖 / 载入最新 / 取消）；他人保存成功经 `draft.saved` 事件通知同草稿其它编辑者。

### M2 · 对象级实时合并（op-log）
- 一端改节点属性（bpmn-js `updateProperties`）→ `POST /design/op` → 服务端盖 **per-`(tenant,defKey)` 单调 `seq`** → 广播 `op` 事件 → 另一端就地 `applyPropTo` 合并。
- **对象级 LWW**：接收端按 `${elementId}::${prop}` → 已应用最大 `seq` 判定，只应用更新的 seq（防乱序/回环覆盖新值）。
- **echo-guard**：op 事件携发送方 `origin` sessionId，发送端据此忽略自己的回声；回放期间 `__applying` 守卫不再回广播。
- **范围边界**：M2 只做**属性级**合并；结构级增删/移动留 M3。

### 架构要点
- **独立事件通道**：协同用一条独立进程内 `tokio::broadcast`（与生命周期 `FlowEvent` 闭合 enum 解耦），自由 JSON payload，承载 `presence` / `draft.saved` / `op` 三类事件。
- **SSE 按 `(tenant, defKey)` 过滤**：补上生命周期 SSE 只按 tenant 过滤的缺口，使「只有同一草稿的编辑者互收对方的在场/选中/编辑」。
- **presence 内存注册表**：`Mutex<HashMap<(tenant,defKey), HashMap<sessionId, Presence>>>` + **sweep-on-build**（构 roster 时剔除超 `TTL=25s` 的会话，免后台任务）。
- **actor 解析**（off 模式）：`current_user()`（X-User 头）→ `body.user` → `anon`；`color_for(user)` 由 user 哈希取 CVD-安全 8 色板，**同人同色跨会话稳定**。

## 二、后端 / API 层测试（26/26）

**方法**：Node 原生 `http` 建 SSE 长连（`Accept: text/event-stream`），逐帧解析 `event:`/`data:`；`fetch` 打 POST 端点（注入 `X-User`）。SSE 与 REST 均用 `default` 租户（off 模式），故 SSE 能收到本 defKey 的广播。脚本：`docs/full-test/fe/collab_backend.cjs`（A–E 组）+ `collab_ttl_sweep.cjs`（TTL 组）。

### A. presence 生命周期（5/5）

| 断言 | 场景 | 实测 |
|---|---|---|
| **A1** join → roster | s1 join（X-User=u_alice, selection=a1）→ SSE `presence` roster 含 s1 | ✅ `user=u_alice sel=a1 color=#008300` |
| **A2** 两 session | s2 join（u_bob）→ roster 含两人 | ✅ `[s1:u_alice, s2:u_bob]` |
| **A3** select 更新 | s1 改选中 `en1` → roster 反映新 selection | ✅ `selection=en1` |
| **A4** 心跳保活+选中 | 心跳携新 selection → 广播更新 | ✅ 广播 |
| **A5** leave | s2 leave → roster 只剩 s1 | ✅ `[s1]` |

### B. SSE 过滤 / 隔离（2/2）

| 断言 | 场景 | 实测 |
|---|---|---|
| **B1** defKey 隔离 | 另开 SSE 订阅 `DK2`；对 `DK` 的 join **不**被 DK2 订阅者收到 | ✅ 隔离正确（无泄漏） |
| **B2** 事件字段完整 | `presence` 事件顶层 `tenant`/`defKey` + roster 项 `sessionId`/`user`/`color` 齐全 | ✅ `tenant=default defKey=… color=#008300` |

### C. 乐观锁防冲突（4/4）

| 断言 | 场景 | 实测 |
|---|---|---|
| **C1** 正确 base 存 | 用当前 `updatedAt` 作 base 保存 → `Saved`（`conflict:false`），`updatedAt` 推进 | ✅ `conflict=false` 时间戳推进 |
| **C2** 过期 base 冲突 | 用**旧** base 再存 → `Conflict`（`conflict:true`）+ `currentUpdatedAt` + `updatedBy` | ✅ `conflict=true current=… by=u_alice` |
| **C3** 无 base 兼容 | `baseUpdatedAt` 不传 → 无条件 `Saved`（向后兼容单人路径） | ✅ `conflict=false` |
| **C4** draft.saved 广播 | 保存成功 → SSE `draft.saved` 事件（含 `updatedAt` + `user`） | ✅ `user=u_alice at=…` |

### D. M2 op 中继（5/5）

| 断言 | 场景 | 实测 |
|---|---|---|
| **D1** 单调 seq | 连发 3 次 op → 服务端盖递增 seq | ✅ `seqs=[1,2,3]` |
| **D2** seq 按 defKey 隔离 | `DK2` 的 op 从独立序列起（非续 DK） | ✅ `DK末=3 DK2=1` |
| **D3** op SSE 广播 | op 广播 `op` 事件，payload `seq`/`origin`/`op`/`elementId`/`props` 完整 | ✅ `seq=4 origin=s1 el=a1 name=最终名` |
| **D4** origin echo-guard | op 事件带 `origin`=发送方 sessionId（供发送端忽略自己） | ✅ `origin=s1` |
| **D5** null 删属性 | `props` 值为 `null` 透传（远端据此删属性） | ✅ null 透传 |

### E. 身份 / actor（off 模式）（3/3）

| 断言 | 场景 | 实测 |
|---|---|---|
| **E1** body.user 兜底 | 无 X-User → `body.user` 定 actor | ✅ `user=body_user` |
| **E2** 同人同色 | 同 user 跨多次事件派生同一色 | ✅ `u_alice` 色集单一 `#008300` |
| **E3** CVD 调色板 | presence 色取自验证过的 CVD-安全 8 色板 | ✅ 色∈板 |

### T. presence TTL sweep（2/2，慢测 ~28s）

| 断言 | 场景 | 实测 |

| **T1** 两人在场 | alive + ghost 两 session join → roster=2 | ✅ `[alive,ghost]` |

## 四、边界与已知限制（M1/M2 明示，非缺陷）

- **单实例**：presence 内存态 + SSE 进程内 bus → 多副本部署不共享（对齐 flow SSE 现状 + 报表单实例假设）。
- **仅 off 鉴权模式**：浏览器 `EventSource` 不能带 header → SSE 只在 `FLOW_AUTH_MODE=off`（本机 dev 默认）可用；jwt 模式浏览器 SSE 鉴权（token-in-query / cookie）留部署期/M2 后续。
- **M2 仅属性级**：结构级增删/移动、以及不经 `applyProp` 的少数编辑（eventDefinition / 变量映射直写 `updateProperties`）不在 M2 同步范围，留 M3。
- **无重连续传**：SSE 断线由 `EventSource` 原生自动重连兜底；presence 靠心跳自愈（感知层可容忍瞬断）。

## 五、结论

设计器协同能力（M1 感知+防冲突、M2 对象级合并）**32 项断言 100% 通过**，覆盖后端 6 端点 + 乐观锁的全部语义、25s TTL 生命周期、SSE 精确隔离，以及双用户真机下的在场感知、远端选中、双向属性实时合并、草稿保存通知与冲突防护——全链路无 pageerror。功能符合设计，边界限制均为 M1/M2 已明示范围（单实例 / off 模式 / 属性级），非缺陷。
