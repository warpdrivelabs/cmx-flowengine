# cmx-flowengine 子流程（callActivity）专项测试报告

> **测试对象**：`cmx-flowengine` 独立流程引擎（`cmx-flow-server` @ `:8091`）的**子流程 / callActivity** 能力
> **测试方式**：真机端到端 REST（`curl`/`jq`，非 mock 非单测）
> **环境**：flow-server `:8091`（jwt + X-API-Key）+ PostgreSQL（`fico` 运行库 / `cmx` 身份+绑定库）
> **日期**：2026-08-16
> **重点覆盖**：**一个主流程上挂多个子流程**（串行 / 并行）、**按组织选择子流程**（精确 / 沿组织树继承 / 深层继承 / 默认兜底 / 禁用跳过 / 多逻辑 key 独立）、父子变量映射、三级嵌套、子流程内退回、边界异常（无绑定 / 取消 / 挂起）

## 2. SUB1 —— 一个主流程上挂多个子流程 ✅ 16/16

### 2.1 串行多子流程（`main_serial_multi`：apply → ①sub_review → ②sub_risk → ③fin_review(组织路由) → pay）

| 断言 | 结果 |
|---|---|
| 串行执行：任一时刻**仅 1 个**子实例（`waitingSubflow=true`） | ✅ |
| ① 挂载 = `sub_review`；① 完成后 ② `sub_risk` 才出现；③ 按 zongbu 路由到 `fin_review_hq` | ✅ |
| 三级子流程 `fin_review_hq` 逐级办结后，父被唤醒到 `pay` 节点 | ✅ |
| 主流程办结 COMPLETED；累计产生 **3 个子实例** | ✅ |

**要点**：验证 [S5.3 多挂载]的核心——同一 token 串行经过多个 callActivity，靠 `(parent_token_id, parent_node_bpmn_id)` 复合键区分挂载点，**不会**因前一挂载已完成而漏起后一挂载。

### 2.2 并行多子流程（`main_parallel_multi`：fork → callFin(组织路由) ‖ callRisk(sub_risk) → join）

| 断言 | 结果 |
|---|---|
| fork 后**两个子实例同时并存**（both ACTIVE，两个 `WaitingSubflow` token） | ✅ |
| callFin 按 fin_sh 路由 → `fin_review_branch`；callRisk → `sub_risk`，二者并存 | ✅ |
| 先办结一支 → 主流程仍 ACTIVE（另一支未完）；两支齐 → join 合流 → 办结 | ✅ |

**要点**：并行网关分叉出的多个挂载点由各自不同的 `Token.id` 区分，子 A 完成只唤醒父 token A，不误触 token B。

## 5.1 发现的缺陷 + 修复（本轮当场修复，全部验证）

测试中在边界路径发现 **2 个真实缺陷**（happy-path 无碍），已按引擎既有范式修复。改动文件：`cmx-flow-engine/src/engine.rs`（+ 同步更新 2 个引擎单测）。修复验证 `sub_fixes_verify.sh` **21/21**。

### 🔴 Bug #1（中）：无绑定子流程泄漏「不可见、不可恢复的僵尸实例」

- **原现象**（修复前实测）：起一个 callActivity 无任何绑定（无默认）的主流程 → `start` 返回 `code=1`「子流程路由无解」，**但响应 `data.id=NULL`**；DB 里却已建实例（`state=ACTIVE`、token 卡 `callGhost/WAITING_SUBFLOW`、`hasIncident=false`）。调用方拿不到 id 却在 `/instances` 列表查得到 → **"启动失败"与"实例存在"矛盾**；补绑定也不自愈，`retry-incident` 空操作，`resume`/`set-variables` 都推不动 → 累积僵尸 ACTIVE 实例。
- **根因**（源码）：`start_process_inner` 先 `create_snapshot`（落库建实例）**后** `launch_subflows_for`（解析路由）。路由 `NoBinding` 时错误向上抛，实例已提交且令牌停在 `WaitingSubflow`（既非 incident 也非终止）。
- **修复**：`launch_one_subflow` 解析失败（无绑定/未部署/未注入 router）**不再抛错**，改为把该挂载点令牌转 **Incident** + 记 `__incident`（对齐 serviceTask 失败语义）——实例保留 Active、`hasIncident=true`、运维台可见、`start` 正常返回 id。并修 `retry_incident`：重激活后补跑 `launch_subflows_for`，使**修好绑定后 retry 能真正续跑**（原来只 `run_to_wait` 会把令牌重新停回 WaitingSubflow，推不动）。
- **验证**（`sub_fixes_verify.sh` Fix#1 组，12 断言）：无绑定 `start` 返回 `code=0`+实例 id、`hasIncident=true`、无子实例、incident 记录原因；补绑定 `retry-incident` 后挂上 `sub_review`、incident 清除、端到端办结。

### 🟠 Bug #2（中）：父实例取消/挂起不级联子流程 → 子被孤立

- **原现象**（修复前实测）：父跑着子流程时 `cancel` → 父 TERMINATED，**子流程仍 ACTIVE**（孤立，继续占用待办）；`suspend` 同理（父 SUSPENDED 子仍 ACTIVE）。孤立子仍可办结但不复活父。
- **根因**：`cancel_process`/`suspend_process` 只作用于目标实例，无 `find_child_instances` 级联。
- **修复**：`cancel_process`/`suspend_process`/`resume_process` 改为 `Box::pin` 递归 async，先对运行中的子实例递归级联（cancel→级联 terminate；suspend→级联 suspend；resume→对称级联恢复），再处理自身。
- **验证**（`sub_fixes_verify.sh` Fix#2 组，9 断言 + SUB4 回归）：父取消→子级联 TERMINATED；嵌套 main 取消→中间+孙**递归**全 TERMINATED；父挂起→子级联 SUSPENDED、父恢复→子级联 ACTIVE 并可端到端办结。
- **说明**：此项上一版报告记为"设计观察"，本轮按"父撤单则子审批作废"的业务直觉**实现为级联**。

## 8. 结论

子流程（callActivity）能力在 cmx-flowengine 上**功能完备且正确**：一个主流程串行/并行挂载多个不同子流程、按发起组织差异化路由（精确/多级继承/默认兜底/禁用跳过）、父子变量双向选择性映射、任意深度嵌套的逐级唤醒、子流程内独立退回——**60 条功能断言全部通过**。

本轮在边界路径发现并**当场修复 2 个缺陷**：① 无绑定子流程曾泄漏"不可见、不可恢复的僵尸实例"→ 改为可见可恢复的 **Incident**（`start` 正常返回 id、`hasIncident=true`、补绑定后 `retry-incident` 续跑）；② 父实例取消/挂起曾**不级联**子流程（子被孤立）→ 改为 **cancel/suspend/resume 级联**（含嵌套递归）。修复后修复专项 **21/21**、子流程回归 **60/60**、主后端回归 **159/159 零回归**，引擎单测全绿（含同步更新的 2 个 m5_2 单测）。所有测试数据持续保留在库，可在门户界面查看与复现。
