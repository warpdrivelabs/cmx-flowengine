## 1. 失控根因（为什么上一轮 CDP 全绿却在门户里失控）

上一轮子流程编辑器是一个 `position:fixed; inset:0; z-index:60` 的**全屏浮层**，渲染在 **property 区**内。

- **demo 壳**（`web/demo/index.html`）：三区堆在**同一个** `<flow-designer>` 组件的**单个 shadow root**里，且组件外层无 `transform`/`contain`。`position:fixed` 相对**视口**定位 → 浮层铺满整屏、关闭按钮在顶部可点 → **看起来正常**，我的 CDP 测试因此全绿。
- **真实门户**：explorer / content / property 被挂成**三个各自独立的 region 宿主**（各自 shadow root），property 是右侧 ~320px 窄面板，其祖先链存在建立 **containing block** 的样式（`transform` / `contain` / `overflow:hidden`）。`position:fixed` 于是相对那个**被裁的窄祖先**定位 → 浮层被困在 320px 窄区里、关闭按钮够不到 → **「覆盖整个页面且无法返回，直接失控」**。

> **教训（关键）**：渲染冒烟 ≠ 结构正确。**多区独立宿主 + 祖先 containing block** 是门户的真实约束；只在 demo 单组件壳上测，会把这类「浮层被祖先裁剪」的结构性缺陷完全掩盖。本轮为此专门造了**门户级多区脚手架**（见 §4）。

---

## 2. 修复方案：四区钻入式（无浮层）

与用户确认两点后落地：**交互＝钻入式复用 content 单一画布**；**「数据模型/model」＝property 区一个可见页签**（门户 model 区是 `display:none` 的隐藏暂存区，渲染不出来，故落到 property 页签，可见、可测、不动菜单/DB）。

四区各司其职（都在两份 `design-workbench.js`，**零后端 / 零菜单改动**）：

| 区 | 主流程 | 钻入子流程后 |
|---|---|---|
| **explorer** | 主流程定义列表 | 组织变体列表（默认兜底/各组织→目标）+「← 返回主流程」+「选组织新建变体」下拉 |
| **content** | 主流程画布 + 工具栏 | **同一个画布**就地切成子流程；工具栏置顶**面包屑**「主流程名 › 子流程名」+ 常驻醒目 **[← 返回主流程]**（在始终可见的工具栏里，**永不被裁**）；保存/发布路由到 `subSave`/`subPublish` |
| **property** | 节点属性 | 页签 **`节点属性 \| 数据模型`**：节点属性照常；数据模型＝内联变量声明编辑器（作用于当前画布 = 子流程变量） |
| **model** | —（门户隐藏，改由 property「数据模型」页签承载） | 同左 |

- **进入**：property 面板「编辑子流程」按钮 或 **双击 callActivity** → `getXml()` 暂存主 XML + 记选中节点 → 把子流程载进 `state.modeler` → 三区刷新。
- **返回** `backToMain()`：脏则确认 → `openDiagram(mainXml)` 还原 + 重选原 callActivity → `subNav=null`。
- **单一 modeler**：`activeModeler()` 简化为恒返 `state.modeler`（钻入只用这一个画布），删除第二个 bpmn-js 实例。

**删除**：`state.subEditor` 全套、`subEditorHtml`/`refreshSubEditor`/`bindSubEditor*`/`bootSubCanvas*`、`.flow-sub-*` 全部 CSS、第二个 bpmn-js 实例、`position:fixed` 浮层（模块 CSS 现零 `position:fixed`）。

## 4. 门户级多区测试脚手架（本轮关键产物）

`fe/subflow_drilldown.cjs` 不再走 demo 单组件壳，而是按**真实门户结构**造脚手架（临时 `web/__mr_harness.html`，测后自删）：

- explorer / content / property 挂成 **3 个各自独立 shadow root** 的宿主（`host.shadowRoot > .native-page-root`，复刻门户 `<cmx-native-pages-host>` 契约）。
- 每个 region 祖先 `overflow:hidden` + **`transform:translateZ(0)`**（造 containing block）→ 复刻门户对 `position:fixed` 的裁剪机制。**若有人再引入全屏浮层，`T1`/`T2` 必红。**
- property 区固定 320px 窄宽（复刻门户）。
- 由真实 loopback 静态服（:9097）提供页面（`route.fulfill` 合成文档会被 Chrome PNA 判为非 loopback 而拦截跨端口 fetch —— 本轮排查所得工程事实）。

> 这套脚手架把「浮层被祖先裁剪」这类**只在多区独立宿主下才暴露**的结构性问题纳入可测范围，堵住上一轮的测试盲区。

## 6. 结论

「覆盖整个页面且无法返回」的失控根因是**全屏浮层在门户多区窄面板祖先的 containing block 里被裁剪**——一个只在真实门户结构下才暴露、被 demo 单组件壳掩盖的结构性缺陷。改为**四区钻入式**（复用 content 单一画布 + 常驻工具栏返回按钮 + explorer 变体列表 + property 数据模型页签）后，经**门户级多区脚手架** 23/23 验证：无浮层、返回永远可达、画布满尺寸、变体切换/新建/保存/发布/数据模型全部正确；主设计器 FE 12/12、后端 60/60 + 159/159 零回归。
